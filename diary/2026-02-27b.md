# 2026-02-27b — Session 46: Cache Serialization Fix (Solfege/Abjad) + Cache Clear Reset + Preset Deactivation Slider Reset

## Bug Fix: Solfege Labels Missing When Loading From Cache

Solfege labels (e.g. "Mi -b3", "Do 2") were not showing on sliders when loading a tuning system from disk cache. They only appeared when fetching fresh from the API.

### Root Cause: Missing Fields in Cache Serialization

`ApiDataCache::pitchClassToJson()` and `jsonToPitchClass()` were missing `solfege` and `abjadName` fields. When pitch class data was fetched from the API, `ApiResponseParser` correctly populated these fields (line 259: `pc.solfege = get("solfege").toString()`). But when the same data was saved to disk and later restored, those two fields were silently dropped.

The serialized fields before the fix:
```
noteName, noteNameDisplay, englishName, fraction, cents, frequency,
pitchClassIndex, octave, midiNoteNumber, midiCentsDeviation, ipnReference, version
```

Missing: `solfege`, `abjadName`.

### Fix

Added both fields to `pitchClassToJson()` (write) and `jsonToPitchClass()` (read) in `ApiDataCache.cpp`:

```cpp
// pitchClassToJson:
obj->setProperty ("solfege",    pc.solfege);
obj->setProperty ("abjadName",  pc.abjadName);

// jsonToPitchClass:
pc.solfege   = get("solfege").toString();
pc.abjadName = get("abjadName").toString();
```

Old cache files on disk don't have these fields — `get()` returns empty `var` for missing keys, so they'll just produce empty strings until the next API fetch or cache clear repopulates them.

## Bug Fix: Cache Clear Doesn't Reset Maqam/Tonic Selectors

Clicking "Clear Cache" in the status bar cleared the disk cache and C++ state, but the maqam and tonic selector dropdowns in the UI retained their previous selection.

### Root Cause: JS-Side Guard Preventing Reset

In `App.tsx`, `syncMaqamStateFromCpp()` has a guard at line 194 designed to prevent stale async events from clearing maqam state:

```tsx
if (!state.selectedMaqamId && (isMaqamModifiedRef.current || selectedMaqamIdRef.current)) {
  // Don't overwrite maqam selection — keep the current state
  return
}
```

When cache is cleared, C++ sends `tuningStateChanged` with empty `selectedMaqamId`. But the guard sees that JS still has a maqam selected (`selectedMaqamIdRef.current` is non-empty) and early-returns, keeping the stale selection.

A second guard at line 234 also blocked degree index clearing:

```tsx
} else if (!isMaqamModifiedRef.current && !selectedMaqamIdRef.current) {
```

If the user had modified a maqam (moved a slider), `isMaqamModifiedRef.current` stayed true and prevented clearing degree highlights.

### Fix: Check `state.systemId` to Distinguish Cache Clear from Async Event

On cache clear, `currentSystemId` is also cleared, so `state.systemId` is empty. Normal async events always have a valid `systemId`. Added this as an escape condition:

```tsx
// Guard 1: allow reset when system is gone (cache cleared)
if (!state.selectedMaqamId && (isMaqamModifiedRef.current || selectedMaqamIdRef.current)
    && state.systemId) {  // ← added: skip guard when no system
  return
}

// Guard 2: always clear when system is gone
} else if (!isMaqamModifiedRef.current && !selectedMaqamIdRef.current
           || !state.systemId) {  // ← added
  if (!state.systemId) isMaqamModifiedRef.current = false  // also reset modification state
  // ... clear degree indices, tonic, etc.
}
```

## Bug Fix: Cache Clear Doesn't Reset Presets

Cache clearing didn't reset the 16 preset slots. After clearing, stale presets remained assigned even though their maqam data was gone.

### Fix

Added preset clearing to `clearCache()` in `PluginProcessor.cpp`:

```cpp
// Reset all presets
for (int i = 0; i < 16; ++i)
    presets[(size_t) i].clear();
savePresetsToDisk();
```

## Bug Fix: Preset Deactivation Doesn't Reset Sliders to Defaults

When clicking an active preset to deactivate it, sliders retained the maqam's variant selections instead of resetting to the closest-to-0-cents defaults.

### Root Cause: PAO Name Matching on Same-System Reload

Preset deactivation calls `bridge.selectTuningSystem(same_system, same_note)` which triggers `loadTuningSystem()`. Inside `doLoad()`:

1. **Step 1** (lines 1094-1106): Select variant closest to 0 cents for each slot — correct!
2. **Step 2** (lines 1109-1124): PAO name matching — re-selects the maqam's variants because `prevPaoNames` still contains the maqam's degree note names from the current slots.

PAO name matching is designed to preserve musical intent when switching between different tuning systems (e.g. a "rāst" note maps to different IPN positions in different systems). But when reloading the same system (preset deactivation), it defeats the purpose of resetting.

### Fix: Skip PAO Matching on Same-System Reload

Detect same-system reload before clearing `currentSystemId`, and skip PAO matching when true:

```cpp
// Before clearing:
const bool sameSystem = (systemId == currentSystemId
                         && startingNote == currentStartingNote);

// In doLoad lambda:
auto doLoad = [this, ..., sameSystem] () {
    // ...
    // PAO name matching (only on system SWITCH, not reload)
    if (!sameSystem)
    {
        for (int i = 0; i < 12; ++i)
            // ... match variants by PAO name
    }
};
```

## Fix: Preset Deactivation Viewport Jump

When deactivating a preset, the slider bank viewport jumped to C3 then flashed back to the preset's tonic position. Two causes:

1. `handlePresetClick(-1)` explicitly reset `stickyViewportRef` to `false` and called `setStartMidi(centerMaqamOctave(48, ...))` — centering on C3.
2. `syncMaqamStateFromCpp()` then received the tuning state event and restored `startMidi` from C++ state without checking `stickyViewportRef`.

### Fix

- Set `stickyViewportRef.current = true` instead of `false` on preset deactivation — keeps the viewport where the user was looking.
- Removed the `setStartMidi(centerMaqamOctave(48, ...))` call.
- Added `!stickyViewportRef.current` guard to the `setStartMidi` call in `syncMaqamStateFromCpp`'s maqam-cleared branch, preventing the C++ state from overriding the sticky position.

## Fix: Preset Deactivation Resets Reference Frequency

`loadTuningSystem()` unconditionally reset `referenceCentsOffset` to 0 and synced the APVTS param. On preset deactivation (same-system reload), the user's reference frequency offset was lost.

### Fix

Wrapped the ref freq reset in `if (!sameSystem)` — the same flag used to skip PAO name matching. System/starting note switches still reset ref freq (new reference point), but preset deactivation preserves it.
