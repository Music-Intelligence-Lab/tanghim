## Session 25: Octave Centering Fix (13 Notes)

### What Changed

**Centering formula corrected** — `centerMaqamOctave()` and the RangeScroller double-click handler both used `visibleCount - 11` to calculate viewport padding. This treated the octave as 12 slider positions (spanning 11 semitone gaps). In reality, a maqam octave includes the tonic's repeat at the top (e.g. C3 through C4 = MIDI 48–60), which is **13 sliders**. The formula now uses `visibleCount - 13`.

**Negative padding guard** — Added `Math.max(0, ...)` around the padding calculation. At minimum width (12 visible sliders), `Math.floor((12 - 13) / 2) = -1` would shift the viewport past the tonic. Clamping to 0 keeps the tonic flush left when the viewport can't fit the full 13-note octave.

### Code Changes

**App.tsx — `centerMaqamOctave()`**:
```typescript
// Before:
const padding = Math.floor((visibleCount - 11) / 2)

// After:
const padding = Math.max(0, Math.floor((visibleCount - 13) / 2))
```

**RangeScroller.tsx — double-click handler**: Same formula change.

**CLAUDE.md** — Updated curtain effect centering documentation.

### Behavior at Different Widths

| Visible sliders | Padding | Result |
|---|---|---|
| 12 (minimum) | 0 | Tonic flush left (can't fit full octave) |
| 13 | 0 | Exact octave: tonic to tonic+12, no extra |
| 14 | 0 | 1 extra slider on right only |
| 15 | 1 | 1 extra on each side, centered |
| 17 | 2 | 2 extra on each side, centered |

### Why 13, Not 12

A maqam spans one octave: from the tonic up to (and including) its repetition one octave above. In slider positions, that's 13 consecutive MIDI notes. The previous formula used 11 (treating 12 positions as spanning 11 gaps), which is an off-by-2 error when the goal is to center 13 physical sliders in the viewport.

## Session 26: Context-Aware Enharmonic IPN Labels via Maqam Detail API

### Problem

Slider IPN labels were hardcoded from a static `IPN_NAMES` array based on chromatic position. This meant the same pitch at chromatic index 6 always showed "F#" — but musically, Saba's 4th degree (ḥijāz) should show "Gb" (since F is already degree III), while Hijaz's 3rd degree should show "F#" (since G is degree IV). The API's maqam detail endpoint provides exactly this context-aware information.

### API Discovery

Verified the DiArMaqAr maqam detail endpoint returns context-aware `ipnReferenceNoteName` per degree:
- `GET /maqamat/maqam_saba?tuningSystem=angloeuropean_1800&startingNote=yegah&pitchClassDataType=all`
  - Degree IV (ḥijāz): `ipnReferenceNoteName: "Gb"`, `englishName: "Gb3"`
- `GET /maqamat/maqam_hijaz?...`
  - Degree III (ḥijāz): `ipnReferenceNoteName: "F#"`, `englishName: "F#3"`

Same pitch, different IPN based on maqam context. Also discovered the `availableTranspositions` field which maps `tonic.idName` → transposition `idName` for fetching transposition-specific detail.

### Architecture

**New struct — `MaqamDetailResult`** (`ApiResponseParser.h`):
```cpp
struct MaqamDetailResult {
    std::vector<PitchClass> ascendingDegrees;
    std::map<juce::String, juce::String> transpositionIdMap;  // tonicId → idName
};
```

**Data flow:**
1. User selects maqam → `applyMaqam()` runs instantly from maqam list cache (existing behavior, unchanged)
2. `applyMaqam()` calls `fetchAndApplyMaqamDetail()` at the end
3. `fetchAndApplyMaqamDetail()` checks maqam detail cache → if hit, applies IPN refs immediately; if miss, fetches from API
4. `applyDegreeIpnRefs()` populates `currentDegreeIpnRefs[12]` — one IPN string per chromatic slot
5. `notifyTuningChanged()` emits tuning state with new `degreeIpnMap`
6. NoteSliderBank uses `degreeIpnMap[chromaticIndex]` when available, falls back to `IPN_NAMES`

**Transposition handling:**
- Base maqam detail provides `availableTranspositions` → `currentTranspositionIdMap`
- Transposition detail is fetched with `&transpositionId=` parameter
- Each transposition is cached separately: key = `systemId:startingNote:maqamId:transpositionId`
- If the transposition map isn't available yet, fetches base maqam first, then re-invokes

### Code Changes

**C++ (6 files modified):**

- **`ApiResponseParser.h`** — Added `MaqamDetailResult` struct, changed `parseMaqamDetail()` return type
- **`ApiResponseParser.cpp`** — Updated `parseMaqamDetail()` to parse `pitchData.ascending` AND `availableTranspositions`

### Edge Cases Handled

- **No maqam selected**: `degreeIpnMap` is empty → all sliders use `IPN_NAMES` (unchanged behavior)
- **Detail not yet loaded**: Labels show default IPN until async fetch completes, then update via `tuningStateChanged` event
- **Tuning system switch**: `currentDegreeIpnRefs` cleared + `currentTranspositionIdMap` cleared
- **Transposition without base detail**: Fetches base maqam first to get `availableTranspositions` map, then re-invokes for transposition
- **User changes maqam during fetch**: Guard check `currentMaqamId != maqId` in callback
- **API error**: Labels stay as default IPN (degree highlighting still works from maqam list data)

### Solfege Consistency (Same Data Source)

After initial implementation, identified that solfege was still sourced from tuning system slot variants while IPN came from maqam detail. This meant IPN and solfege could be inconsistent (e.g., "Gb3" with "Fa#3"). Extended the feature to also source solfege from the maqam detail:
- Added `currentDegreeSolfegeRefs[12]` alongside `currentDegreeIpnRefs[12]`
- Added `degreeSolfegeMap` to tuning state JSON (parallel to `degreeIpnMap`)
- NoteSliderBank uses `degreeSolfegeMap[chromaticIndex]` when available, falls back to variant solfege
- API currently returns non-context-aware solfege (e.g. "Fa#3" for Gb), but the API author will fix this — plumbing is in place for when it does

### Key Design Decisions

1. **Same source for IPN and solfege** — Both come from the maqam detail API, ensuring consistency
2. **Async fetch, not blocking** — Maqam selection remains instant (from maqam list data). IPN/solfege labels update asynchronously when detail arrives
3. **Separate cache directory** — `~/Library/Tanghim/cache/maqam-detail/` keeps maqam detail separate from tuning system data
4. **No UI changes for non-degree sliders** — Only degree slots get context-aware IPN/solfege. Non-degree sliders keep tuning system defaults
5. **Reusing existing parseSinglePitchClass()** — Maqam detail ascending degrees use the same PitchClass parsing. Both `ipnReferenceNoteName` and `solfege` fields are already read

## Session 28: Reference Frequency Control

### What Was Built

A global concert pitch control ("Ref Freq") that shifts all 128 MTS-ESP frequencies by a cents offset. The control lives in the top-bar's right column, alongside the MTS-ESP status badges.

### Architecture

**Internal model**: `referenceCentsOffset` (double, default 0.0, range ±700 cents). Applied as a global frequency multiplier in `TuningEngine::updateTuning()` after building the per-slot frequency table:
```cpp
if (referenceCentsOffset != 0.0) {
    const double ratio = std::pow(2.0, referenceCentsOffset / 1200.0);
    for (auto& f : newFreqs) f *= ratio;
}
```

**Hz computation** (for display only):
```
defaultHz = 440 * 2^((referenceNoteMidi - 69) / 12)  // pure 12TET
currentHz = defaultHz * 2^(referenceCentsOffset / 1200)
```

`referenceNoteMidi` is the MIDI note of the tonic in octave 1 (from pitch class data with `pitchClassIndex==0, octave==1`). Changes when the starting note changes.

**APVTS parameter**: `ref_freq` (`AudioParameterFloat`, ±700.0, step 0.01) — exposed for DAW automation. Gesture marking via `beginRefFreqGesture()`/`endRefFreqGesture()` for proper automation recording.

**State persistence**: `referenceCentsOffset` saved/restored in `getStateInformation()`/`setStateInformation()`.

## Session 29: Fix MIDI Device Persistence & Realtime Updates

### Problem

The MIDI device input for Preset MIDI Map Config had two issues:
1. **Not updating in realtime** — plugging in/unplugging a MIDI device didn't update the dropdown until the plugin was closed and reopened
2. **Settings not working on DAW relaunch** — although the chosen device name persisted in `settings.json`, the device didn't actually open on relaunch

### Root Cause Analysis

**Bug 1 (settings erased on editor open) — the main "doesn't work on relaunch" cause:**

`populateMidiDeviceList()` was called during editor construction. It used `ComboBox::setSelectedId()` without `juce::dontSendNotification`, which fired the `onChange` callback → `onMidiDeviceChanged()` → `setMidiPresetDevice("")` → `saveSettingsToDisk()`. This **overwrote the saved device name with `""`** every time the plugin window was opened.

The sequence:
1. Processor constructor → `loadSettingsFromDisk()` → `setMidiPresetDevice("MyDevice")` → device opens successfully
2. Editor created → `setupMidiPresetControls()` → `populateMidiDeviceList()`
3. `setSelectedId(1)` fires `onChange` → `onMidiDeviceChanged()` → `setMidiPresetDevice("")` → closes device → saves `""` to disk
4. Next relaunch reads `midiPresetDevice: ""` → no device opened

Confirmed by inspecting `~/Library/Tanghim/settings.json` — `midiPresetDevice` was `""` despite the user having selected a device.

**Bug 2 (no realtime updates):**

The dropdown was populated once in `setupMidiPresetControls()` at editor construction. No polling mechanism existed to detect newly connected/disconnected MIDI devices.

**Bug 3 (no retry on startup):**

If the MIDI device wasn't available when the Processor constructor ran (e.g. USB device still initializing), `setMidiPresetDevice()` silently failed with no retry. The device would never open until the user manually reselected it.

### Fix

**1. `dontSendNotification` in `populateMidiDeviceList()`** (PluginEditor.cpp)

All `setSelectedId()` and `clear()` calls now pass `juce::dontSendNotification` to prevent firing `onChange` during programmatic updates. The callback only fires on actual user interaction with the dropdown.

**2. Realtime device list polling** (PluginEditor.cpp timerCallback)

Added to the 2Hz timer section: polls `getAvailableMidiDevices()`, compares against `lastKnownMidiDevices` (new `juce::StringArray` member in Editor), and calls `populateMidiDeviceList()` when the list changes. Newly connected/disconnected devices appear within ~0.5s.

**3. Device open retry** (PluginEditor.cpp timerCallback)

In the same 2Hz timer block: if `getMidiPresetDevice()` is non-empty but `!isMidiPresetDeviceOpen()`, retry `setMidiPresetDevice()`. This handles the case where the device wasn't available at Processor construction but becomes available shortly after.

**4. `isMidiPresetDeviceOpen()` method** (PluginProcessor.h/.cpp)

New public method: `return midiPresetInput != nullptr;` — allows the Editor to check if the configured device was actually opened.

### Key JUCE Insight

`ComboBox::setSelectedId()` defaults to `sendNotificationAsync` for its notification type. This means calling it programmatically (e.g. during initialization) triggers the `onChange` callback, which can cause unintended side effects. Always use `juce::dontSendNotification` when setting ComboBox values from code rather than from user interaction.

| `source/PluginProcessor.cpp` | Added `isMidiPresetDeviceOpen()` implementation |
| `source/PluginEditor.h` | Added `lastKnownMidiDevices` member for device list change detection |

## Session 30: Internal Reference Oscillator

### What Was Built

An internal polyphonic triangle-wave oscillator for reference pitch audition. Users can now hear the microtuned pitches directly from the Transmitter plugin — useful for verifying synth tuning against the expected maqam intonation. The oscillator is **additive**: it runs alongside MTS-ESP, MPE, and Pitch Bend simultaneously.

### Architecture

**New file — `source/engine/TriangleOscillator.h`** (header-only):

Two structs, no `.cpp` file needed:

- **`OscVoice`**: Single voice with phase accumulator, frequency, and linear envelope
  - Triangle formula: `4.0 * abs(phase - 0.5) - 1.0` (naive, no band-limiting — fine for reference use)
  - Envelope: 5ms linear attack (no click on note-on), 100ms linear release (clean tail)
  - Methods: `noteOn()`, `noteOff()`, `nextSample()`, `updateFrequency()`

- **`TriangleOscillator`**: Manages 16 pre-allocated voices (no audio-thread allocation)
  - `prepare(sampleRate)` — called from `prepareToPlay()`
  - `noteOn(midiNote, freqHz)` — re-trigger check → free voice search → round-robin steal
  - `noteOff(midiNote)` — releases first matching active voice
  - `processSample()` — sums all active voices, returns mono double
  - `allNotesOff()` — releases all voices (called when toggling off)

**Integration in `PluginProcessor`**:

- `oscillatorEnabled` (`std::atomic<bool>`) — lock-free read from audio thread
- `setOscillatorEnabled(bool)` — atomic exchange; if transitioning true→false, calls `allNotesOff()`
- `prepareToPlay()` — calls `oscillator.prepare(sampleRate)` (was previously a no-op)
- Both `processBlock()` overloads (float and double):
  1. On Note On/Off: also calls `oscillator.noteOn()`/`noteOff()` with frequency from `tuningEngine.getFrequencyForMidiNote()`
  2. Updates active voice frequencies per buffer (live slider drag feedback — tuning changes heard immediately)
  3. Sample loop: `oscillator.processSample() * 0.125` (-18 dBFS) added to all channels after `audio.clear()`
- `getTailLengthSeconds()` changed from `0.0` to `0.15` (100ms release tail needs DAW to keep processing)

**State persistence**: `oscillatorEnabled` saved/restored in:
- `getStateInformation()` / `setStateInformation()` (DAW session state)
- `saveSettingsToDisk()` / `loadSettingsFromDisk()` (global settings)

**Bridge**: `setOscillatorEnabled(bool)` — fire-and-forget, registered in `NativeBridge::applyTo()`. `oscillatorEnabled` added to `buildTuningStateJson()`.

### UI — "Osc" Badge

Added a clickable "Osc" badge as the **leftmost** badge in `OutputModeSelector`, before MTS-ESP:

- Warm coral color (`#ffab91`), cursor: pointer, hover opacity
- Click toggles oscillator on/off via optimistic state update + bridge call
- Active = full opacity, inactive = 0.5 opacity (uses existing `.mts-badge-inactive` class)
- No count span (it's a toggle, not a counter — unlike MTS-ESP/MPE/Mono PB)

### Key Design Decisions

1. **No APVTS parameter** — The oscillator is a utility toggle, not a musical parameter to automate
2. **Header-only** — Simple enough to avoid CMakeLists.txt changes
3. **16 voices** — Sufficient for chord verification; all pre-allocated
4. **-18 dBFS** — Quiet enough for reference, loud enough to hear clearly
5. **Frequency update per buffer** — Active voices' `phaseInc` updated from TuningEngine at buffer start (one CriticalSection acquire per voice), ensuring slider drag updates are heard immediately
6. **Thread safety** — `oscillatorEnabled` is atomic; `allNotesOff()` on disable from message thread is benign (worst case: a voice starts releasing one sample early)

## Session 31: MIDI Device Persistence Fix + Preset Channel Filtering

### Problem 1: MIDI device not reconnecting on fresh load

The MIDI preset device dropdown showed the correct device name on plugin reload, but the device wasn't actually receiving MIDI — the user had to reselect the same device to make it work.

**Root cause:** Two issues combined:

1. **Unnecessary close+reopen**: `setMidiPresetDevice()` unconditionally closed and reopened the MIDI device, even when called with the same device name that was already open. During startup, `loadSettingsFromDisk()` opens the device, then `setStateInformation()` calls `setMidiPresetDevice()` again with the same name — closing the working CoreMIDI connection and attempting to reopen. This close+reopen cycle could fail silently.

2. **Empty session state clearing settings.json device**: If a DAW session was saved before a MIDI device was configured (or in a different project), `setStateInformation()` would receive an empty `midiPresetDevice` string. Since empty string is not `void`, the old code called `setMidiPresetDevice("")`, which closed the working device AND cleared `midiPresetDeviceName` — killing the 2Hz retry mechanism in the editor timer.

**Fix:**
- Added early return in `setMidiPresetDevice()`: if the requested device name matches the current name AND the device is already open (`midiPresetInput != nullptr`), skip the close+reopen entirely
- In `setStateInformation()`: only call `setMidiPresetDevice()` if the session state has a non-empty device name — don't let an empty session value override a working device from settings.json

### Problem 2: Preset MIDI channel triggering oscillator + activity

When the user's MIDI controller was routed through the DAW to the Tanghim plugin, notes on the preset trigger channel would both switch presets (via the direct MIDI input) AND trigger the internal oscillator + MIDI activity feedback (via `processBlock()`).

**Fix:** Added channel filtering at the top of both `processBlock()` overloads (float and double). When `midiPresetChannel` is set to a specific channel (1-16), all MIDI messages on that channel are skipped (`continue`) before oscillator/activity processing. When set to "All" (0), no filtering is applied since there's no way to distinguish preset MIDI from performance MIDI.
