# 2026-02-19 — Session 14: Remove Output Mode from Transmitter

## Summary

Removed the output mode selector (MTS-ESP / MPE / Pitch Bend) from the Transmitter plugin. The Transmitter now exclusively broadcasts via MTS-ESP — output mode selection is the Receiver's responsibility. The UI selector was replaced with a read-only MTS-ESP connection status display.

---

## Architectural Decision

### Why Remove Output Mode?

The Transmitter had a 3-mode selector (MTS-ESP, MPE, Pitch Bend), but this was architecturally redundant:

1. **MTS-ESP** works directly — any MTS-ESP-aware synth reads tuning from shared memory. No Receiver needed.
2. **MPE / Mono PB** always require a Receiver plugin between the Transmitter and the synth.
3. Multiple Receivers can coexist on different tracks, each independently choosing MPE or Mono PB.

Having mode selection on both Transmitter and Receiver was confusing and unnecessary. The Transmitter's only job: **broadcast tuning via MTS-ESP**. The Receiver independently decides how to deliver it.

## M4L Fixes (from earlier in session)

## Plugin Rename: Arabic Maqam Tuner → Tanghim

### The Rename Journey

Renamed all user-facing plugin references from "Arabic Maqam Tuner" to "Tanghim" (the Arabic word for tuning/intonation). The process revealed several DAW/build constraints:

1. **First attempt**: `"Tanghīm (transmitter)"` — JUCE's CMake post-build `cmake -E remove` command doesn't quote paths, so parentheses `()` in PRODUCT_NAME cause a shell syntax error: `/bin/sh: -c: line 0: syntax error near unexpected token '('`

2. **Second attempt**: `"Tanghīm – transmitter"` (en-dash U+2013) — built successfully but Ableton's VST3 scanner garbled the UTF-8: displayed as "Tangh圮m 亍妤 transmitter" (CJK characters)

3. **Extended ASCII investigation**: ī (U+012B, Latin i with macron) is NOT in ISO 8859-1, Windows-1252, or any common "Extended ASCII" codepage. Macron vowels only exist in ISO 8859-4 (Baltic), which DAWs don't use.

4. **Final solution**: Pure ASCII `"Tanghim"` / `"Tanghim Receiver"` for all DAW-facing names (PRODUCT_NAME, `getName()`, scale name, Receiver editor title). UTF-8 `"Tanghīm"` kept only in the WebView UI `<title>`, which is rendered by WebKit and not constrained by DAW text handling.

### Files Changed
- `CMakeLists.txt` — PRODUCT_NAME, BUNDLE_ID, CLAP_ID
- `source/PluginProcessor.h` — `getName()` return value
- `source/PluginProcessor.cpp` — `buildScaleName()` default
- `source/PluginEditor.cpp` — Windows webview cache path
- `source/receiver/ReceiverEditor.cpp` — title label
- `source/api/ApiDataCache.cpp` — cache directory name
- `ui/index.html` — page title (UTF-8 "Tanghīm")
- `ui/package.json` — package name
- `m4l/generate_patch.py` — output paths, title, plug_vst3 message
- `m4l/mts_midi_effect.js` — comment

### Key Finding
**VST3 plugin names MUST be pure ASCII for Ableton compatibility.** The VST3 scanner (runs as x86_64 on Apple Silicon) cannot handle UTF-8 or any non-ASCII encoding in plugin bundle names or display names.

## Session 15: Live MTS-ESP Status Polling + Receiver Type Badges

### Problem
1. **No live polling**: MTS-ESP receiver count only queried during tuning state changes (slider/maqam select). Plugins loaded after the Transmitter aren't detected until the user loads a maqam.
2. **No type distinction**: Single badge `"MTS-ESP · N receivers"` doesn't distinguish between MTS-ESP-native synths and our Receivers in MPE or Mono PB mode.

### Architecture Decision: File-Based Receiver Registry

The MTS-ESP API only provides `MTS_GetNumClients()` — a single count with no client enumeration or metadata. Since Transmitter and Receiver are separate VST3 bundles, they can't share in-process state. Solution: file-based IPC via `~/Library/Tanghim/receivers/`.

Each Receiver instance writes `{uuid}.mpe` or `{uuid}.monopb` to the registry directory. The file extension encodes the mode. A 1Hz heartbeat touches the file (updates mtime). The Transmitter scans at ~2Hz, ignoring stale files (mtime > 5s).

MTS-ESP native count = `MTS_GetNumClients()` - (MPE receivers + Mono PB receivers).

## Session 16: UI Polish — Smooth Scrolling, Receiver Theme, Maqam Selector Enhancements

### Smooth Slider Viewport Scrolling

Changed `startMidi` from integer to float for pixel-level smooth scrolling. Mouse wheel delta is now proportional (`deltaY / SLOT_WIDTH_PX`) instead of `Math.sign()`. NoteSliderBank renders an extra slider with CSS `translateX(-pixelOffset)` for sub-pixel offset. RangeScroller uses `step="any"` for smooth dragging.

### Maqam Octave Centering

When selecting a maqam or applying a preset, the viewport now auto-centers on the maqam's octave: `startMidi = tonicMidi - floor((visibleCount - 12) / 2)`, clamped to valid range. Double-clicking the RangeScroller also centers on the current maqam.

### Receiver Editor Redesign

Replaced the JUCE-default ComboBox/Slider with a custom dark navy theme matching the Transmitter's CSS:
- `ReceiverLookAndFeel` class with matching colour palette
- Two toggle buttons (MPE / Mono PB) instead of ComboBox
- PB range value box with +/- buttons and editable text instead of slider
- Manual APVTS sync via 5Hz timer (replaced ComboBox/Slider attachments)
- Fixed garbled Unicode: `juce::String::charToString(0x2212)` for minus sign, `juce::String::charToString(0x2014)` for em dash (raw UTF-8 byte literals don't work reliably in JUCE Labels)

### MTS-ESP Scale Name Enhancement

Added `currentMaqamDisplay` and `currentTonicDisplay` to PluginProcessor, populated during `applyMaqam()`. Scale name now broadcasts as `"maqām rāst / rāst — Ibn Sīnā (1037)"` instead of just the tuning system name. Persisted in plugin state.

### Transposition Dropdown Sorting + Labels

Sorting transposition dropdown items by the tuning system's native pitch order required compound sort key `(octave, pitchClassIndex)` from pitch class data — not just `pitchClassIndex` alone, because register-specific names (qarār, jawāb) share the same `pitchClassIndex` across octaves.

Added `paoOrder` (unique PAO idNames in ascending pitch order) and `paoNameInfo` (PAO idName → `{englishName, solfege}`) to tuning state JSON. The `solfege` field was already in the API response but not parsed — added to `PitchClass` model and `ApiResponseParser`.

Transposition labels now show: `"segāh / E-b3 / Mi -b3 (qarār)"` — PAO display name + IPN + solfège, with "(qarār)" suffix for the base tonic.
