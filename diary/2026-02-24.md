## Session 38: CPU Performance Optimization

### Problem

Plugin was using 2-3% CPU when freshly loaded in a DAW with no MIDI activity, and up to 5% when playing the internal reference oscillator. Unacceptable for a MIDI utility plugin.

### Phase 1: Idle CPU (2-3% → near-zero)

**Root cause analysis:**
- `processBlock` was doing unnecessary work every buffer even when idle (MidiBuffer iteration, heptatonic remapping, oscillator voice scanning)
- `ReceiverRegistry::scan()` at 2Hz doing filesystem directory iteration
- `juce::MidiInput::getAvailableDevices()` at 2Hz doing CoreMIDI enumeration

**Fixes applied:**

1. **processBlock early return** (`PluginProcessor.cpp`, both float and double overrides):
   ```cpp
   if (midi.isEmpty() && (! oscOn || ! oscillator.hasActiveVoices()))
       return;
   ```
   Added `hasActiveVoices()` to `TriangleOscillator` for this check.

2. **Guard MIDI buffer processing** — wrapped the heptatonic remapping + PB tracking block in `if (! midi.isEmpty())` to skip MidiBuffer construction/iteration when no MIDI present.

3. **Rate-limited filesystem I/O** — moved `ReceiverRegistry::scan()` and stale cleanup from 2Hz to ~0.2Hz (every 5 seconds) via `slowPollCounter` in the editor timer. MTS-ESP shared memory reads (cheap) remain at 2Hz.

### Phase 2: Event-Driven MIDI Device Enumeration

**Root cause:** `juce::MidiInput::getAvailableDevices()` was polled at 2Hz, doing a full CoreMIDI enumeration each time.

**Fix:** Replaced polling with `juce::MidiDeviceListConnection::make()` — JUCE 8's cross-platform event-driven API that fires a callback only when MIDI devices connect or disconnect.

```cpp
// Constructor
midiDeviceListConnection = juce::MidiDeviceListConnection::make ([this]
{
    midiDevicesChanged.store (true, std::memory_order_relaxed);
});
```

- Atomic flag `midiDevicesChanged` set by the callback, checked in the 2Hz timer tick
- Cross-platform: uses CoreMIDI notifications on macOS, WinMM on Windows, ALSA on Linux
- Removed `lastKnownMidiDevices` StringArray comparison (was also doing CoreMIDI enumeration)
- Initial flag set to `true` to populate list on first timer tick

**Files changed:** `PluginEditor.h` (new members), `PluginEditor.cpp` (constructor, destructor, timerCallback, setupMidiPresetControls)

### Phase 3: Oscillator Hot-Path Rewrite (5% → lower)

**Root cause analysis** (using JUCE Context7 documentation):

| Issue | Impact |
|---|---|
| `audio.addSample(ch, s, sample)` per-sample per-channel | Bounds check + indirect pointer + isClear flag per call |
| `processSample()` iterates all 16 voices per sample | 8192 iterations/buffer (512 samples × 16 voices), most returning 0.0 |
| No `ScopedNoDenormals` | Denormalized floats during envelope release cause CPU spikes |
| `getFrequencyForMidiNote()` per voice | CriticalSection lock acquisition per active voice per buffer |
| Per-sample inner channel loop | Prevents SIMD optimization |

**Fixes applied:**

1. **`juce::ScopedNoDenormals noDenormals`** at top of both processBlock overrides — prevents denormalized float penalties on x86/ARM during envelope release tails.

2. **Block-based voice rendering** (`TriangleOscillator::renderBlock()`):
   - Two overloads: `float*` and `double*`
   - Iterates only active voices, each processing its full block contiguously
   - Better cache locality than interleaved per-sample across all 16 voices
   - Inactive voices are skipped entirely (no per-sample branch)

   ```cpp
   void renderBlock (float* output, int numSamples, float gain)
   {
       for (auto& v : voices)
       {
           if (! v.active) continue;
           for (int s = 0; s < numSamples; ++s)
               output[s] += static_cast<float> (v.nextSample()) * gain;
       }
   }
   ```

3. **Direct pointer writes** — `audio.getWritePointer(0)` for channel 0, then `juce::FloatVectorOperations::copy()` (SIMD-accelerated) for remaining channels. Eliminates `addSample()` overhead entirely.

4. **Frequency table snapshot** (`TuningEngine::snapshotFrequencyTable()`):
   - Copies entire 128-note frequency table under one CriticalSection lock
   - Previously each active voice called `getFrequencyForMidiNote()` with its own lock acquisition
   - Cleaner code and guaranteed consistent table across all voices

5. **Reference frequency fast path** (`TuningEngine::updateReferenceOffset()`):
   - New `baseFreqTable` member caches the frequency table before reference offset
   - `setReferenceCentsOffset()` now calls `updateReferenceOffset()` instead of full `updateTuningAndBroadcast()`
   - Avoids rebuilding the entire 128-note table + cents table + scale name on every ref freq knob drag tick

### Performance Audit Report (additional findings, not yet implemented)

Priority items identified during the comprehensive audit for future consideration:

1. **CriticalSection → double-buffered frequency table** (TuningEngine) — eliminate lock contention between message thread writes and audio thread reads. Use atomic index swap between two table copies.

2. **SpinLock + String::fromUTF8() allocation on audio thread** (ReceiverProcessor) — `currentScaleName` updated under SpinLock with heap-allocating String construction. Should move to message-thread timer or use fixed-size char buffer.

3. **`setValueNotifyingHost()` ×128 from audio thread** (ReceiverProcessor) — triggers DAW automation infrastructure per call. Should batch and defer to message thread timer.

4. **`noteStack.reserve(16)` in MonoPitchBendProcessor** — `std::vector<int>` without reserve risks audio-thread heap allocation on first push_back.

5. **Pre-allocate MidiBuffers as members** (ReceiverProcessor) — avoid per-processBlock MidiBuffer construction for `filtered` and `output` locals.
