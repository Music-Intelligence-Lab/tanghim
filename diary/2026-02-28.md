# 2026-02-28 — Session 47: MIDI Preset Trigger Parity with UI Click

## Bug: MIDI Preset Triggering Not Working Same as UI Click

MIDI input for preset triggering (via the dedicated MIDI device) behaved differently from clicking a preset button in the UI.

### Root Cause: Two Separate Code Paths

The editor timer consumed `pendingMidiPreset` and called `processor.applyPreset()` + `emitTuningStateChanged()` directly in C++ — bypassing the entire JS `handlePresetClick()` pipeline. This meant MIDI-triggered presets missed:

1. **Viewport centering** — `handlePresetClick` centers on the maqam's tonic octave
2. **`fetchAndApplyMaqamDetail`** — context-aware IPN labels and solfege for the selected maqam
3. **Modification tracking** — comparing slot cents against expected variants for modified state detection (cyan thumbs, asterisk suffix)
4. **`presetIndexOverrideRef`** — guarding against async `tuningStateChanged` overwriting the active preset index
5. **System switch handling for modified presets** — modified presets store their tuning system, requiring `bridge.selectTuningSystem()` with `afterSystemSwitchRef` callback

The C++ `applyPreset()` only handled the raw slot application (degree indices, cents offsets, maqam ID, tonic), none of the rich UI behavior.

### Fix: Route MIDI Triggers Through JS `handlePresetClick`

Changed the editor timer to emit a `midiPresetTriggered` JS event instead of calling C++ directly:

**`source/PluginEditor.cpp`** (timer callback):
```cpp
// Before:
processor.applyPreset (presetIdx);
emitTuningStateChanged();

// After:
auto* obj = new juce::DynamicObject();
obj->setProperty ("presetIndex", presetIdx);
browser->emitEventIfBrowserIsVisible ("midiPresetTriggered",
                                       juce::var (obj));
```

**`ui/src/App.tsx`** — added event handler:
```tsx
useJuceEvent('midiPresetTriggered', (data: unknown) => {
  if (!data || typeof data !== 'object') return
  const { presetIndex } = data as { presetIndex: number }
  if (typeof presetIndex === 'number') handlePresetClick(presetIndex)
})
```

Now MIDI and UI preset triggers share the exact same code path — `handlePresetClick()` — which handles all the rich behavior including:
- Applying the preset via C++ bridge
- Centering viewport on maqam tonic
- Fetching maqam detail for context-aware labels
- Tracking modification state
- Handling system switches for modified presets
- Setting `presetIndexOverrideRef` to guard against async overwrites

### Also Fixed: `centerOnMaqam` Block Was Empty

The `centerOnMaqam` block in `syncMaqamStateFromCpp` was an empty `if` body — it detected when viewport centering was needed (e.g., session recall with a maqam) but never actually centered. Filled the block:

```tsx
if (centerOnMaqam && !stickyViewportRef.current) {
  setStartMidi(centerMaqamOctave(tonicMidi, fractionalVisibleCount))
}
```

Added `!stickyViewportRef.current` guard to respect sticky viewport (preset deactivation scenario).

# Session 48: Release Build Fixes

## Fix 1: `withResourceProvider` Allowed Origin Type Mismatch

The Release-only `#if EMBED_UI_BUNDLE` code path passed `juce::URL(getResourceProviderRoot())` as the `allowedOriginIn` parameter, but JUCE 8's `withResourceProvider` expects `std::optional<String>`. `getResourceProviderRoot()` already returns `const String&`, so the `juce::URL` wrapper was unnecessary and broke compilation.

**Fix:** Pass `getResourceProviderRoot()` directly (it's already a `String`).

```cpp
// Before:
juce::URL (juce::WebBrowserComponent::getResourceProviderRoot())
// After:
juce::WebBrowserComponent::getResourceProviderRoot()
```

## Fix 2: BinaryData Resource Lookup — Dashes Removed, Not Replaced

The main issue. The plugin loaded in Release mode but showed a blank white WebView. The native status bar rendered fine (it's JUCE-native, not WebView).

### Root Cause

Vite generates hashed filenames with dashes: `index-2ZL2UqSZ.js`, `index-DP3Qwh1W.css`. JUCE BinaryData **removes** dashes from resource names (not replaces with `_`):

| Original filename | BinaryData name | Old code produced |
|---|---|---|
| `index-2ZL2UqSZ.js` | `index2ZL2UqSZ_js` | `index_2ZL2UqSZ_js` ✗ |
| `index-DP3Qwh1W.css` | `indexDP3Qwh1W_css` | `index_DP3Qwh1W_css` ✗ |
| `index.html` | `index_html` | `index_html` ✓ |

The old `replaceCharacters("./- ", "____")` approach replaced `-` with `_`, so asset lookups all failed. `index.html` loaded fine (no dashes), but the JS and CSS it referenced couldn't be found, resulting in a blank page.

### Fix

Instead of trying to mangle the path to match JUCE's naming rules (which are complex and version-dependent), match the requested filename against `BinaryData::originalFilenames[]` and use the corresponding `BinaryData::namedResourceList[]` entry:

```cpp
auto filenameOnly = cleanPath.fromLastOccurrenceOf ("/", false, false);
if (filenameOnly.isEmpty()) filenameOnly = cleanPath;

for (int i = 0; i < BinaryData::namedResourceListSize; ++i)
{
    juce::String orig (BinaryData::originalFilenames[i]);
    if (orig == filenameOnly)
    {
        data = BinaryData::getNamedResource (BinaryData::namedResourceList[i], size);
        break;
    }
}
```

This is robust against any future JUCE BinaryData naming changes. The directory prefix is stripped first since BinaryData flattens the directory structure.
