## Session 33: MIDI Clip Export Encoding + Name Format

### Problem

Dragging MIDI clips from the plugin into Ableton showed garbled names like `maqƒÅm_rƒÅst_al-rƒÅst_C3_Do3`. The UTF-8 bytes for Arabic transliteration diacritics (ā, ī, ū, etc.) were being interpreted as Mac Roman by Ableton's MIDI parser.

**Root cause:** MIDI SMF text meta events (FF 03 track name) are encoded as raw bytes. Ableton interprets these as Mac Roman (macOS legacy encoding), not UTF-8. UTF-8 multi-byte sequences for characters like `ā` (U+0101: bytes 0xC4 0x81) map to `ƒÅ` in Mac Roman.

### Approaches Tried

1. **Removed track name entirely** — Ableton showed "Track 0" and drag-to-Finder broke. Track name is required.
2. **ASCII transliteration** — Map Arabic transliteration diacritics to base ASCII (ā→a, ī→i, ū→u, ḥ→h, ṣ→s, ḍ→d, ṭ→t, ẓ→z, ġ→g). This became the final solution.

### Final Implementation

**`source/engine/MidiFileGenerator.cpp`** — Three new helper functions:

- **`toAscii()`** — Maps 18 Arabic transliteration code points (9 lowercase + 9 uppercase) to ASCII equivalents. Unknown non-ASCII chars replaced with `-`.
- **`sanitizeForFilename()`** — Replaces `/`, `:`, `\` with `-` (PAO names can contain `/` which breaks `getChildFile()`).
- **`buildNameBase()`** — Shared helper for the new format: `maqamname_(PAOname-IPN-solfege)`.

**Track name** uses ASCII transliteration (for DAW compatibility).
**Filename** keeps UTF-8 (for filesystem display): `maqām_rāst_(rāst-C3-Do3).mid`.

**`source/PluginEditor.h`** — MidiDragButton fixes:
- Added `dragStarted` guard flag to prevent `performExternalDragDropOfFiles` from being called multiple times per drag gesture.
- Changed `canMoveFiles` from `false` to `true`.

**`source/PluginEditor.cpp`** — Temp file location changed from `juce::File::tempDirectory` to `~/Library/Tanghim/midi-export/`.

### Key Insight: Mac Roman Encoding

Ableton (and likely other DAWs) use Mac Roman for MIDI text events. The MIDI SMF spec doesn't mandate an encoding, and Mac Roman is the macOS legacy default. The only safe approach is ASCII-only track names. UTF-8 can be used in filenames since the OS handles those correctly.

## Session 34: Chronological Tuning System Sorting

### Problem

Tuning systems in the dropdown appeared in API response order (arbitrary). Needed chronological sorting, including letter suffixes (950a, 950b, 950c...).

### Investigation

1. **C++ sort logic** — Added `std::sort` by `year` (integer) then `yearStr` (string) in `ApiDataCache::setTuningSystemsList()` and `loadFromDisk()`. Initially hoped the API's `year` field contained the suffix (e.g. "950a").

2. **API reality** — The `year` field is just an integer (950, not "950a"). The letter suffix only exists in the `displayName` (e.g. "al-Fārābī (950a) First Oud Tuning...").

3. **`yearStr` field added** to `TuningSystem` struct, `ApiResponseParser`, `ApiDataCache`, `NativeBridge`, and TypeScript types — but it's just the integer as a string (e.g. "950"), not useful for suffix sorting.

4. **UI was re-sorting alphabetically** — `TuningSystemSelector.tsx` had a `localeCompare` sort that overrode any C++ ordering.

### Final Solution (UI-side)

Removed the alphabetical sort from `TuningSystemSelector.tsx` and added chronological sort:
```typescript
const sorted = useMemo(() =>
  [...systems].sort((a, b) => a.year !== b.year ? a.year - b.year : a.displayName.localeCompare(b.displayName)),
  [systems]
)
```

Since the `displayName` contains the year with suffix in parentheses (e.g. "al-Fārābī (950a)..."), `localeCompare` on `displayName` naturally orders "950a" before "950b" when years are tied.

Also removed `shortName || displayName` fallback — uses `displayName` directly (per project rule: no fallbacks).

## Session 35: Heptatonic Keyboard Mode

### Overview

Implemented heptatonic keyboard mode — remaps MIDI input so the 7 maqam scale degrees are playable on white keys, with the tonic staying on its natural keyboard position. Toggled via a "Hept" badge (lavender) in the `OutputModeSelector` bar.

### Design Evolution (across two sessions)

The implementation went through three iterations before arriving at the final design:

#### Iteration 1: C-starting mapping (initial)
White keys C,D,E,F,G,A,B always mapped to degrees 1-7. For G Rast: pressing C played G (tonic). Used `heptMap` storing output chromatic indices. **Problem**: octave wrapping broken for non-C tonics.

#### Iteration 2: C-starting with semitone deltas
Changed `heptMap` from chromatic indices to signed semitone deltas. Formula: `rawNote + delta`. Computed "adjusted" chromatic values with octave wrapping (`while (adjusted[i] <= adjusted[i-1]) adjusted[i] += 12`). Black keys used delta of nearest white key below. **Fixed**: octave wrapping. **Problems**: (1) Deltas were large (7-13 semitones for non-C tonics), breaking Mono PB receivers (2st default range). (2) User preferred tonic on its natural key.

#### Iteration 3: Tonic-preserving mapping (final)
White keys rotate from the tonic's position. G tonic: G,A,B,C,D,E,F map to degrees 1-7. Deltas are small (typically ±1-2 semitones). Black keys get delta 0 (play natural chromatic pitch). **Fixed**: Mono PB compatibility, intuitive keyboard layout.

### Key Architectural Insight: MTS-ESP Table Remapping

The critical challenge was that Ableton's inter-track MIDI routing sends the original input MIDI notes, not the plugin's modified output events. Investigation confirmed the JUCE VST3 wrapper DOES correctly write modified MIDI to output events (`MidiEventList::pluginToHostEventList`), but Ableton ignores them when routing between tracks.

**Solution: Dual approach**
1. **processBlock MIDI rewrite**: `midi.swapWith(remapped)` for same-track consumers (internal oscillator, MIDI activity bitmask, DAWs that properly route MIDI output)
2. **MTS-ESP frequency table remap**: `freq[originalNote] = internalFreq[originalNote + delta]` so MTS-ESP synths receiving un-remapped MIDI notes still play correct pitches

This required:
- `TuningEngine::broadcastMtsTable()` — push a frequency table to MTS-ESP without modifying internal state
- `TuningEngine::rebroadcastCurrentTuning()` — re-push internal table (used when hept disabled)
- `updateTuningAndBroadcast()` — wraps all 11 `tuningEngine.updateTuning()` call sites, applies hept remap if active
- `rebroadcastHeptMts()` — builds remapped table and broadcasts to MTS-ESP

### Tonic-Preserving Mapping Algorithm

```
Input: degreeChroms[7] — chromatic indices of 7 degrees in degree order
       tonicChrom — chromatic index of tonic (degree 0)

1. Find tonic's position in white key array [0,2,4,5,7,9,11]
   - Exact match first (most common: C,D,E,F,G,A,B are typical tonics)
   - Black-key tonic: nearest white key using circular distance, prefer lower on tie

2. Initialize all 12 deltas to 0 (black keys = chromatic passing tones)

3. For each degree i (0-6):
   whiteKey = whiteKeys[(tonicWhiteIdx + i) % 7]
   delta = degreeChroms[i] - whiteKey
   Normalize to [-6, +5] range (minimal adjustment)
   deltas[whiteKey] = delta

4. Store deltas in heptMap[12] atomics
```

**Examples:**
| Maqam | Degrees | White key deltas (non-zero only) |
|-------|---------|----------------------------------|
| Rast on C | C,D,E♭½,F,G,A,B | All 0 (fits white keys perfectly) |
| Rast on G | G,A,B♭½,C,D,E,F# | F→F# (Δ+1) |
| Hijaz on D | D,E♭,F#,G,A,B♭,C | E→Eb (Δ-1), F→F# (Δ+1), B→Bb (Δ-1) |
| Bayati on D | D,E♭½,F,G,A,B♭,C | B→Bb (Δ-1) |

### Active Note Tracking

Rather than `allNotesOff()` on every map rebuild:
- `activeHeptNotes[128]` (atomic ints, -1 = inactive) tracks inputNote → remappedNote for held notes
- **Note On**: remap using current heptMap, store in activeHeptNotes, use remapped note for oscillator + bitmask
- **Note Off**: look up activeHeptNotes to get the mapping from when Note On was sent
- **Maqam change / map rebuild**: no allNotesOff — held notes sustain at original mapping, new notes use updated map
- **Hept toggled off**: allNotesOff + clear activeHeptNotes (notes were remapped, need clean release)

### Why Tonic-Preserving Works for All Output Modes

| Mode | Mechanism | Why small deltas matter |
|------|-----------|------------------------|
| **Internal oscillator** | processBlock rewrites MIDI → oscillator uses remapped notes | N/A (direct frequency lookup) |
| **MTS-ESP native** | Remapped freq table: `freq[C] = freq[C+Δ]` | N/A (frequency directly assigned) |
| **MPE** | Remapped freq table → Receiver computes PB from deviation | 48st default PB range handles any delta |
| **Mono PB** | Remapped freq table → Receiver computes PB from deviation | ±1-2st deltas fit within 2st default range |

The old C-starting approach had deltas up to +13 semitones (e.g., C→F# for G Rast 7th degree), which exceeded Mono PB's 2st range. The tonic-preserving approach keeps max delta at ±2st for typical maqamat.
