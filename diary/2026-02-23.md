## Session 33: MIDI Clip Export Encoding + Name Format

### Problem

Dragging MIDI clips from the plugin into Ableton showed garbled names like `maqƒÅm_rƒÅst_al-rƒÅst_C3_Do3`. The UTF-8 bytes for Arabic transliteration diacritics (ā, ī, ū, etc.) were being interpreted as Mac Roman by Ableton's MIDI parser.

**Root cause:** MIDI SMF text meta events (FF 03 track name) are encoded as raw bytes. Ableton interprets these as Mac Roman (macOS legacy encoding), not UTF-8. UTF-8 multi-byte sequences for characters like `ā` (U+0101: bytes 0xC4 0x81) map to `ƒÅ` in Mac Roman.

### Approaches Tried

1. **Removed track name entirely** — Ableton showed "Track 0" and drag-to-Finder broke. Track name is required.
2. **ASCII transliteration** — Map Arabic transliteration diacritics to base ASCII (ā→a, ī→i, ū→u, ḥ→h, ṣ→s, ḍ→d, ṭ→t, ẓ→z, ġ→g). This became the final solution.

### Final Implementation

**`source/engine/MidiFileGenerator.cpp`** — Three new helper functions:

- **`toAscii()`** — Maps 18 Arabic transliteration code points (9 lowercase + 9 uppercase) to ASCII equivalents. Unknown non-ASCII chars replaced with `-`.
- **`sanitizeForFilename()`** — Replaces `/`, `:`, `\` with `-` (PAO names can contain `/` which breaks `getChildFile()`).
- **`buildNameBase()`** — Shared helper for the new format: `maqamname_(PAOname-IPN-solfege)`.

**Track name** uses ASCII transliteration (for DAW compatibility).
**Filename** keeps UTF-8 (for filesystem display): `maqām_rāst_(rāst-C3-Do3).mid`.

**`source/PluginEditor.h`** — MidiDragButton fixes:
- Added `dragStarted` guard flag to prevent `performExternalDragDropOfFiles` from being called multiple times per drag gesture.
- Changed `canMoveFiles` from `false` to `true`.

**`source/PluginEditor.cpp`** — Temp file location changed from `juce::File::tempDirectory` to `~/Library/Tanghim/midi-export/`.

### Key Insight: Mac Roman Encoding

Ableton (and likely other DAWs) use Mac Roman for MIDI text events. The MIDI SMF spec doesn't mandate an encoding, and Mac Roman is the macOS legacy default. The only safe approach is ASCII-only track names. UTF-8 can be used in filenames since the OS handles those correctly.

## Session 34: Chronological Tuning System Sorting

### Problem

Tuning systems in the dropdown appeared in API response order (arbitrary). Needed chronological sorting, including letter suffixes (950a, 950b, 950c...).

### Investigation

1. **C++ sort logic** — Added `std::sort` by `year` (integer) then `yearStr` (string) in `ApiDataCache::setTuningSystemsList()` and `loadFromDisk()`. Initially hoped the API's `year` field contained the suffix (e.g. "950a").

2. **API reality** — The `year` field is just an integer (950, not "950a"). The letter suffix only exists in the `displayName` (e.g. "al-Fārābī (950a) First Oud Tuning...").

3. **`yearStr` field added** to `TuningSystem` struct, `ApiResponseParser`, `ApiDataCache`, `NativeBridge`, and TypeScript types — but it's just the integer as a string (e.g. "950"), not useful for suffix sorting.

4. **UI was re-sorting alphabetically** — `TuningSystemSelector.tsx` had a `localeCompare` sort that overrode any C++ ordering.

### Final Solution (UI-side)

Removed the alphabetical sort from `TuningSystemSelector.tsx` and added chronological sort:
```typescript
const sorted = useMemo(() =>
  [...systems].sort((a, b) => a.year !== b.year ? a.year - b.year : a.displayName.localeCompare(b.displayName)),
  [systems]
)
```

Since the `displayName` contains the year with suffix in parentheses (e.g. "al-Fārābī (950a)..."), `localeCompare` on `displayName` naturally orders "950a" before "950b" when years are tied.

Also removed `shortName || displayName` fallback — uses `displayName` directly (per project rule: no fallbacks).

### C++ Changes (from previous session, committed together)

- **`source/model/TuningSystem.h`** — Added `yearStr` field
- **`source/api/ApiResponseParser.cpp`** — Store `yearStr` from API year field
- **`source/api/ApiDataCache.cpp`** — Sort in `setTuningSystemsList()` + `loadFromDisk()`, persist `yearStr`
- **`source/NativeBridge.cpp`** — Send `yearStr` to UI
- **`ui/src/types/index.ts`** — Added `yearStr` to `TuningSystem` interface

## Session 34b: Remove Slider Bank Scroll + RangeScroller Magnetic Snap

### What Changed

**Removed mouse/trackpad horizontal scrolling** from the slider bank:
- Removed `onWheel={handleBankWheel}` from the slider bank container div
- Removed `handleBankWheel` callback, `isUserScrolling` state, `userScrollTimeoutRef`
- Removed all `setIsUserScrolling(false)` calls throughout App.tsx (maqam select, preset load, system switch, etc.)
- The `isUserScrolling` flag was specifically for wheel-based scrolling — it prevented auto-centering during user scroll gestures. With wheel removed, auto-centering always applies.

**RangeScroller magnetic snap:**
- Changed from `step={1}` (integer snap) to `step="any"` with magnetic snap logic
- When the thumb is within 1.1 MIDI notes of a tick mark (C, G, or A), it snaps to it
- Otherwise moves freely (fractional positions)
- Tick marks remain at every C (pitch class 0), G (7), and A (9) position
