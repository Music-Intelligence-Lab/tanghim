# 2026-02-26 — Sessions 43–44

## Summary

Fixed two bugs related to `.tanghim` file loading and maqam modification tracking:

1. **Modification detection on load** — cyan modified-degree thumbs were not appearing after loading a `.tanghim` file with a modified maqam. Root cause: the counter-based event skip in `handleLoadState` was consuming the wrong `tuningStateChanged` event.

2. **Maqam association on slider edit** — modifying a slider previously cleared `currentMaqamId` and `currentDegreeNames`, which broke degree highlights, heptatonic map, and `.tanghim` save/load. Now only the preset is deactivated; maqam association is preserved.

## Bug 1: Counter-Based Event Skip Race Condition

### Symptoms
After loading a `.tanghim` file containing a modified maqam, the slider thumbs showed gold (unmodified maqam degree) instead of cyan (modified maqam degree). The maqam name also lacked the ` *` modification suffix. Slider positions were correctly restored.

### Root Cause
The `handleLoadState` callback used a counter (`isFirstEvent`) to skip exactly one intermediate event (from `loadTuningSystem`'s cleared state) and process the second event (from `restoreStateFromJson`'s restored state). However, a pending `tuningStateChanged` event from a previous action (e.g., slider drag, maqam selection) could arrive between setting the callback and the load events. This stale event consumed the "first event" skip, causing the actual first event (with cleared maqam state) to be processed as the "second" event — which had empty `selectedMaqamId` and `degreeNames`, so no modification was detected.

### Diagnosis
Added `console.log` to the callback, which showed:
```
[loadState] callback Event #2: {maqamId: "", degreeNamesLen: 0, degreeNames: []}
```
This confirmed the callback was processing an event with cleared (intermediate) maqam state, not the restored state.

### Fix: Content-Based Event Matching
Replaced the counter-based approach with content-based matching. The callback now skips ALL events that lack maqam data (`selectedMaqamId` empty or `degreeNames` empty) and processes the first event that has both. This is robust against any number of intermediate or stale events.

For files without maqam data, the callback is consumed after `bridge.loadStateFile()` returns, using the `hasMaqam` flag from C++ to distinguish the two cases.

**Before (fragile):**
```javascript
let isFirstEvent = true
afterSystemSwitchRef.current = (newState) => {
  if (isFirstEvent) { isFirstEvent = false; return false }
  // process newState (might be the wrong event!)
}
```

**After (robust):**
```javascript
afterSystemSwitchRef.current = (newState) => {
  if (!newState.selectedMaqamId || !newState.degreeNames?.length) {
    return false  // keep waiting — intermediate or stale event
  }
  // process newState (guaranteed to have maqam data)
}
// After await: consume callback if file has no maqam
if (!result.hasMaqam && afterSystemSwitchRef.current) {
  afterSystemSwitchRef.current = null
}
```

## Bug 2: buildDegreePaoNameMap Register-Specific Name Overwrite

### Problem
`buildDegreePaoNameMap` maps chromatic index → PAO name for each maqam degree. For a maqam spanning more than one octave (e.g., ascending [rāst, dūgāh, ..., kirdan]), the last degree with a given chromatic index overwrites earlier ones. "kirdan" (C4, register-specific) overwrites "rāst" (C3, base register) for chromatic index 0. Since slot variants only cover MIDI 48-59 (base register), `slot.variants.find(v => v.noteName === "kirdan")` fails → modification not detected for the tonic.

### Fix
Changed to only use the first occurrence per chromatic index (`!result.has(ci)`). Ascending degrees start from the base register, so the first name is always the base-register name that matches slot variants.

## Bug 3: Preserve Maqam Association on Slider Edit

### Problem (pre-existing, fixed in this session)
`setSliderVariant`, `setSlotCents`, and `setNoteVariant` cleared `currentMaqamId`, `currentTranspositionIdx`, and `currentDegreeNames` when the user manually adjusted a slider. This meant:
- Degree highlights disappeared after editing
- Heptatonic map broke after editing
- `.tanghim` save after editing didn't include maqam data (so load couldn't restore it)

### Fix
Only `currentActivePresetIdx` is cleared (deactivates the preset). Maqam ID, transposition index, and degree names are preserved. Comment updated to explain the design intent.

# Session 44: UI Polish — Gold Maqam Selectors, Preset Override Guard, Non-Degree Modification Tracking, Gold Maqam Snap Markers

## Summary

Five UI improvements in a single session:

1. **Gold maqam selectors** — maqam and tonic dropdown triggers turn gold (border + background fill + text) when a maqam is selected but no preset is active
2. **Preset override persistence** — `presetIndexOverrideRef` no longer consumed on first use, preventing async `fetchAndApplyMaqamDetail` events from deactivating presets ~2s after selection
3. **Non-degree modification tracking** — non-maqam-degree slots now tracked in `modifiedSlots` with teal (#00b0a0) thumbs/markers, distinct from maqam degree cyan (#26c6da)
4. **Non-degree default revert** — clicking a snap marker that matches the slot's default variant (closest to 0 cents) removes it from modified set, reverting to default red style
5. **Gold maqam snap markers** — the snap marker matching the maqam's expected degree variant is gold on hover and when active; other markers remain red
6. **File dialog directory memory** — save/load `.tanghim` dialogs remember the last used directory for the session

## Gold Maqam Selectors (No Preset Active)

### Design
When a maqam+tonic is selected from the dropdown (not via preset), the maqam and transposition `CustomSelect` triggers should visually indicate the active maqam with gold styling — matching the gold accent used throughout for maqam-related UI. When a preset is active, the preset button is gold and the selectors stay in their default state to avoid double gold.

### Implementation
- Added `activePresetIndex` prop to `MaqamSelector`
- Computed `goldFill = selectedMaqamId && activePresetIndex < 0`
- Applied `gold-fill` CSS class to both `CustomSelect` wrappers conditionally
- CSS: `.gold-fill .cs-trigger` → `border-color: #d4a843`, `background: rgba(212, 168, 67, 0.1)`, `color: #d4a843`

## Preset Override Persistence Fix

### Problem
After selecting a preset, the preset correctly activated (gold button), but ~2 seconds later it deactivated and the maqam selectors turned gold instead. Root cause: `presetIndexOverrideRef` was consumed on the first `syncMaqamStateFromCpp` call (set to `null`). When `fetchAndApplyMaqamDetail` completed ~2s later and fired `tuningStateChanged` with `activePresetIndex: -1` (C++ `applyMaqam` clears `currentActivePresetIdx`), the override was gone and `-1` took effect.

### Fix
Changed `syncMaqamStateFromCpp` to only consume the override when C++ confirms the preset index matches (`state.activePresetIndex === presetOverride`). Async events sending `-1` no longer clear the override. The override is explicitly cleared on:
- Preset deactivation (`handlePresetClick(-1)`)
- Slider modification (`handleCentsDrag` when `maqamModifiedRef` flips)
- Snap marker click (`handleVariantSelect`)

Also set `presetIndexOverrideRef` in both `applyUnmodifiedPreset` and `applyModifiedPreset` (previously only `handleMaqamSelect` set it).

## Non-Degree Modification Tracking

### Problem
Only maqam degree slots were tracked in `modifiedSlots`. Non-degree (passing tone) slots showed no visual indication when modified.

### Implementation
- `handleCentsDrag`: now adds non-degree slots to `modifiedSlots` when a maqam is selected
- `handleVariantSelect`: non-degree snap marker clicks track as modified; clicking the default variant (closest to 0 cents) removes from modified set
- `handleLoadState`: load callback detects non-degree modifications by comparing `slot.centsOffset` to the default variant's `midiCentsDeviation`
- CSS: `.note-slider.modified .thumb` → teal `#00b0a0` (base rule); `.note-slider.maqam-degree.modified .thumb` → cyan `#26c6da` (higher specificity override)

## Gold Maqam Snap Markers

### Problem
All snap markers used red accent for hover and active state. The marker corresponding to the maqam's expected degree should use gold.

### Implementation
- Added `maqamDegreePaoNames` prop to `NoteSliderBank` (passed from `App.tsx`)
- Per slot, find the variant index matching the maqam's expected PAO name → `maqamVariantIndex`
- Passed to `NoteSlider` as prop, applied as `maqam-default` CSS class on the matching snap marker
- CSS: `.snap-marker.maqam-default:hover` and `.snap-marker.maqam-default.active` → `#ffc947` gold

## File Dialog Directory Memory

### Implementation
- Added `lastTanghimDirectory` member to `NativeBridge`
- Both save and load dialogs check `lastTanghimDirectory.isDirectory()` — if valid, use it as start directory; otherwise fall back to `userDocumentsDirectory`
- Updated to parent directory of the chosen file after each successful save or load

## Additional Changes (Same Session)

### Sticky Viewport for Wide Windows
When the slider bank shows 24+ sliders and the user manually drags the RangeScroller, the viewport becomes "sticky" — selecting different maqamat or presets no longer auto-centers on the tonic octave. This lets users keep their preferred view range while browsing maqamat on wide displays.

- `stickyViewportRef` (boolean ref) set to `true` when `handleRangeScrollerChange` fires and `fractionalVisibleCount >= 24`
- All `setStartMidi(centerMaqamOctave(...))` calls guarded by `!stickyViewportRef.current` (except `.tanghim` file load, which always centers)
- Sticky resets when: viewport shrinks below 24 sliders, maqam is cleared, or tuning system is changed

### Tonic Border Layout Shift Fix
Maqam tonic slider's gold border (and equiv's dimmed border) used CSS `border` which adds to the element's box, shifting text content inward when the maqam is selected. Switched to `outline` + `outline-offset: -1px` which renders without affecting layout.
