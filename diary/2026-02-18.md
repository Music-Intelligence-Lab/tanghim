## Maqam List Caching

### Problem
`fetchMaqamListIfNeeded()` always hit the API directly — unlike `fetchSetsIfNeeded()` which properly checked the disk cache first. The maqam list (all available maqamat + transpositions for a tuning system) was never persisted.

2. **`ApiDataCache.cpp`** — full JSON serialization/deserialization of `MaqamListEntry` including nested `MaqamDegrees` (ascending/descending string arrays) and `MaqamTransposition` vectors.
3. **`PluginProcessor.cpp`** — `fetchMaqamListIfNeeded()` now checks cache first, stores to cache after API fetch.

### Problem

## Universal Binary for Ableton Compatibility

### Problem
Plugin wasn't showing up in Ableton 11 at all. Ableton's PluginScanner.txt revealed:
```
error: Failed to load plugin: The bundle "Arabic Maqam Tuner" couldn't be loaded because it doesn't contain a version for the current architecture.
```

The plugin was built as arm64-only, but Ableton 11's VST3 plugin scanner runs as x86_64 (even on Apple Silicon Macs).

### Fix
Added `-DCMAKE_OSX_ARCHITECTURES="arm64;x86_64"` to all CMake configure commands. This produces a universal binary that works in both native arm64 and Rosetta/x86_64 contexts.

### VST3 Install Path
`~/Library/Audio/Plug-Ins/VST3/` — the macOS user-level system folder scanned by Ableton's "Use VST3 Plug-In System Folders" setting.

### Key Lesson
**Always check DAW plugin scanner logs** when a plugin doesn't appear. For Ableton 11: `~/Library/Preferences/Ableton/Live {version}/PluginScanner.txt`.

## MIDI Effect — No Audio Buses

### Problem
Plugin was recognized by Ableton but classified as an audio effect rather than a MIDI-only effect. Ableton routed audio through it and wouldn't let it sit purely in the MIDI chain before an instrument.

### Root Cause
The `PluginProcessor` constructor declared stereo audio buses:
```cpp
AudioProcessor (BusesProperties()
    .withInput  ("Input",  juce::AudioChannelSet::stereo(), true)
    .withOutput ("Output", juce::AudioChannelSet::stereo(), true))
```
VST3 has no native "MIDI effect" category. When a plugin declares audio buses, hosts like Ableton treat it as an audio processor — regardless of `IS_MIDI_EFFECT=TRUE` or `isMidiEffect()` returning true.

### Fix (Attempt 1 — failed)
Changed to empty `BusesProperties()` with no audio buses. This caused Ableton to reject the plugin entirely: "This VST3 plug-in could not be opened." Ableton **requires at least one audio output bus** to load any VST3.

### Fix (Attempt 2 — working)
Changed to output-only stereo bus, no input:
```cpp
AudioProcessor (BusesProperties()
    .withOutput ("Output", juce::AudioChannelSet::stereo(), true))
```
This gives Ableton the minimum audio bus it needs to instantiate the plugin. Combined with `IS_MIDI_EFFECT=TRUE`, the plugin is classified as a MIDI effect and doesn't process incoming audio.

### Key Lesson (superseded)
The output-only MIDI effect approach was later abandoned in favour of IS_SYNTH=TRUE (see below).

## Instrument Classification (IS_SYNTH=TRUE)

### Problem
Even with `IS_MIDI_EFFECT=TRUE` and output-only buses, Ableton 11 still required an instrument to be placed before the plugin on a MIDI track. Third-party VST3 MIDI effects cannot occupy the pre-instrument slot in Ableton — only Ableton's built-in MIDI effects can. The ODDSound MTS-ESP Master plugin solves this by classifying as an **instrument** (`IS_SYNTH=TRUE`).

### Fix
Changed classification from MIDI effect to instrument:
- `CMakeLists.txt`: `IS_SYNTH TRUE`, `IS_MIDI_EFFECT FALSE`, `VST3_CATEGORIES "Instrument" "Tools"`
- `PluginProcessor.h`: `isMidiEffect()` returns `false`
- Restored stereo in+out `BusesProperties` (Ableton needs audio buses)

### Code Signing Issue
After the classification change, the plugin didn't appear in Ableton at all. Scanner log revealed: `"Failed to load plugin: a sealed resource is missing or invalid"`. CMake's build process leaves a broken code signature. Fixed by adding post-build re-signing:
```bash
codesign --force --deep --sign - "build/ArabicMaqamTuner_artefacts/Debug/VST3/Arabic Maqam Tuner.vst3"
```

### Audio Buffer Clearing
As an instrument, Ableton sends uninitialized audio buffers expecting the plugin to fill them. The plugin was outputting noise because `processBlock` used `juce::ignoreUnused(audio)`. Fixed by changing to `audio.clear()` in both float and double `processBlock` overloads.

### Key Lesson
For a JUCE VST3 that acts as a MIDI-only instrument in Ableton:
1. `IS_SYNTH TRUE` + `IS_MIDI_EFFECT FALSE` in CMakeLists.txt
2. `isMidiEffect()` returns `false`
3. Stereo in+out `BusesProperties` (Ableton requires audio buses)
4. `audio.clear()` in `processBlock` to silence the buffer
5. Post-build `codesign --force --deep --sign -` to fix broken signature

## Ableton MIDI Routing Limitation

MPE and Pitch Bend data does not pass between tracks in Ableton — it merges all MIDI to channel 1 when routing. This is why ODDSound created Max for Live wrapper devices for their MTS-ESP MIDI Client. For our plugin:
- **MTS-ESP mode**: Works perfectly in Ableton (global, no MIDI routing needed)
- **MPE/Pitch Bend modes**: For DAWs that support placing MIDI effects before instruments (Logic, Reaper, etc.)

### Future: Receiver Plugin
A separate "Receiver" plugin (MIDI effect) will be needed for non-MTS-ESP synths. Unlike the current "Transmitter" (instrument/MTS-ESP master), the Receiver will:
- Sit before synths and apply pitch bend/MPE retuning directly
- Need a Max for Live wrapper for Ableton (same approach as ODDSound)
- Work standalone as a MIDI plugin in other DAWs (Logic, Reaper, etc.)

Terminology: **Transmitter** (not Master) and **Receiver** (not Client/Slave) — avoiding colonial/racist language

## MTS-ESP Stale Note Filters Fix

### Problem
Some notes weren't sounding on MTS-ESP receiver synths (e.g. Arturia DX7). Notes were being received via MIDI but simply not played.

### Root Cause
MTS-ESP shared memory persists across sessions. The note filter state from a previous MTS-ESP master (e.g. ODDSound) was still active, causing receiver synths to filter (skip) certain notes via `MTS_ShouldFilterNote()`.

### Fix
Added `MTS_ClearNoteFilter()` immediately after `MTS_RegisterMaster()` in `MtsEspTransmitter` constructor. Also push an initial 12-EDO tuning table so receivers have valid frequency data from the moment of registration.

### Key Lesson
Always clear MTS-ESP note filters and push an initial tuning table right after registering as transmitter. Shared memory state can persist from previous sessions or other MTS-ESP master plugins.

## MTS-ESP IPC Recovery

### Problem
After rebuilding and reinstalling the plugin, MTS-ESP receivers no longer connected. The stale shared memory from the previous plugin instance persisted (the old destructor may not have called `MTS_DeregisterMaster()`), causing `MTS_CanRegisterMaster()` to return false.

### Fix
Implemented the IPC recovery pattern from the MTS-ESP API header. The `MtsEspTransmitter` constructor now:
1. Try `MTS_CanRegisterMaster()` — normal path
2. If that fails, check `MTS_HasIPC()` — if true, stale shared memory from a crash
3. Call `MTS_Reinitialize()` to reset everything, then `MTS_RegisterMaster()`
4. If `MTS_HasIPC()` is false, another real transmitter is active — stay inert

Added DBG logging at each decision point for diagnosing future issues.

## Cache Performance: Lazy Loading + Incremental Saves

### Problem 1: Cache data not persisting
The `ApiDataCache` only called `saveToDisk()` in the destructor (`~ApiDataCache`). If the DAW crashed or force-quit, the destructor never ran and cache data was lost. Additionally, `updateSets()` and `updateMaqamList()` only modified in-memory state — the on-disk cache files only contained pitch classes (stored via `storeData()` during the API callback), while maqam lists and twelve-pitch-class sets were always empty in the cached JSON.

### Problem 2: Slow startup loading
`loadFromDisk()` deserialized ALL cached JSON files at startup — every tuning system the user had ever visited (25 files, 1.8MB total). This happened synchronously in the PluginProcessor constructor, blocking the UI.

### Fix
Rewrote `ApiDataCache` with two key changes:

**1. Incremental saves** — each `storeData()`, `updateSets()`, `updateMaqamList()`, and `updateLastChecked()` immediately writes the modified entry to disk. Cache directory is created eagerly in the constructor. No more reliance on destructor-only saving.

**2. Lazy loading** — `loadFromDisk()` now only scans file names (stored as `lazyKeys` set), not file contents. Actual JSON deserialization happens on first `getData()` call via `ensureLoaded()`. This means only the active tuning system gets deserialized, not all 25.

**Minor optimisations:**
- `reserve()` calls on all vectors before deserialization loops
- Direct `(double)` cast instead of `.toString().getDoubleValue()` for numeric fields
- Removed `saveToDisk()` public method entirely (no longer needed)

### Results
- Startup scan: 2.2ms (was ~50-100ms+ for full deserialization of 25 files)
- Individual entry deserialization: on-demand, only when accessed
- Cache writes: immediate, 2-11ms per entry
- Cross-platform: all file operations use JUCE's `File` API (macOS, Windows, Linux)

### Key Lesson
Never rely solely on destructor-based persistence in plugin environments — DAWs may crash, force-quit, or fail to call destructors properly. Write cache data incrementally as it arrives. Use lazy loading to avoid deserializing data that may never be needed in the current session.

# Session 10 — Receiver Plugin

## MTS-ESP Receiver Plugin

### Goal
Create a lightweight MIDI effect plugin that reads tuning from the MTS-ESP transmitter and applies it via MPE or monophonic pitch bend — for synths that don't natively support MTS-ESP.

### Implementation
Added a new CMake target `ArabicMaqamTunerReceiver` alongside the existing transmitter. Four new source files:

**`source/receiver/ReceiverProcessor.h/.cpp`**:
- Registers as MTS-ESP Client (`MTS_RegisterClient()` / `MTS_DeregisterClient()`)
- Each `processBlock`: queries `MTS_RetuningInSemitones()` for all 128 notes → builds cents deviation table
- Filters notes via `MTS_ShouldFilterNote()` — unmapped notes are skipped
- Routes through existing `MpePitchBendProcessor` or `MonoPitchBendProcessor` based on mode
- 3 APVTS parameters: mode (MPE/Pitch Bend), MPE PB range (default 48st), Mono PB range (default 2st)
- State save/recall via APVTS XML serialization

**`source/receiver/ReceiverEditor.h/.cpp`**:
- Minimal JUCE-native editor (~360×210px) — no React/WebView
- ComboBox for mode selection, Slider for PB range (shows active mode's range)
- Status label updates at 5Hz: "Connected — [scale name]" or "No transmitter found"
- Version label from `PLUGIN_VERSION` compile definition

**CMake target**:
- `IS_SYNTH=FALSE`, `IS_MIDI_EFFECT=TRUE` — appears in MIDI FX slots
- Links MTS-ESP Client (`libMTSClient.cpp`) instead of Master
- Reuses `MpePitchBendProcessor.cpp` and `MonoPitchBendProcessor.cpp`
- CLAP support via `clap-juce-extensions`
- `JUCE_WEB_BROWSER=0` — no WebView needed

### Key Design Decisions
- **Reuse existing pitch bend processors**: Both `MpePitchBendProcessor` and `MonoPitchBendProcessor` accept a `std::array<double, 128>& centsDeviationTable` — the receiver just builds this from MTS-ESP queries instead of from `ActiveTuningState`
- **Separate PB ranges**: MPE defaults to 48 semitones, Mono to 2 semitones — matches the transmitter's behavior and avoids user having to readjust on mode switch
- **Query per block, not per note**: 128 × `MTS_RetuningInSemitones()` calls per block is trivial, and ensures tuning changes from the transmitter are picked up immediately
- **Stereo audio buses**: Originally `BusesProperties()` with no I/O, but Max's `vst~` requires audio buses to display the editor. Changed to stereo in/out with `audio.clear()` in processBlock.

## Session 11 — Receiver Crash Fixes & Max for Live Wrapper

### Max for Live Wrapper
Built a Max for Live MIDI Effect (`.amxd`) to host the Receiver in Ableton, since Ableton doesn't support VST3 MIDI effects natively. Patch: `midiin` → `midiparse` → `vst~ "Arabic Maqam Tuner Receiver" 2 2` → outlet 4 → `route midievent` → `midiout`. Key learnings:
- `midiparse` rightmost outlet auto-formats `midievent` messages for `vst~` (from Cycling74 docs)
- VST3 in `vst~`: named MIDI messages (`note`, `control`) don't work — only `midievent` format
- `vst~` outlet 4 is for VST3-generated MIDI events
- `sig~ 0.` feeds silence to vst~ audio input

### Thread Safety Fix
Crash #1: Editor's `timerCallback()` called `MTS_HasMaster()` and `MTS_GetScaleName()` on the message thread while `processBlock()` called them on the audio thread. Fix: moved ALL MTS-ESP calls to the audio thread, cached results in `std::atomic<bool> connectedToMaster` and `SpinLock`-protected `juce::String currentScaleName`.

### MTS-ESP Always-Broadcast Fix
Receiver showed "12 TET" even when Transmitter had a maqam loaded — because `TuningEngine::updateTuning()` only broadcast via MTS-ESP when in MTS-ESP output mode. Fix: removed the mode guard so tuning is always broadcast to MTS-ESP shared memory regardless of the Transmitter's own MIDI output mode.

### bendValue() Undefined Behavior Fix (Crash Root Cause)
Receiver still crashed after the broadcast fix. Root cause: `bendValue()` in both `MpePitchBendProcessor` and `MonoPitchBendProcessor` had undefined behavior:

```cpp
// BEFORE (UB):
const int bv = 8192 + (int) std::round (ratio * 8192.0);
return std::clamp (bv, 0, 16383);
```

When `MTS_RetuningInSemitones()` returns extreme values (NaN/Inf from malformed frequency tables), `std::round(∞)` returns infinity, and casting infinity to `int` is **undefined behavior** in C++ — the crash happens before `std::clamp` can save it.

```cpp
// AFTER (safe):
if (std::isnan (centsDeviation) || std::isinf (centsDeviation)) return 8192;
const double raw = 8192.0 + std::round (ratio * 8192.0);
return static_cast<int> (std::clamp (raw, 0.0, 16383.0));
```

Also added NaN/Inf guard in `ReceiverProcessor::processBlock()` when building the cents table from `MTS_RetuningInSemitones()`.

### Key Lesson
Always validate floating-point values before integer casts — `(int) std::round(inf)` is UB. Clamp on the `double` side first, then cast to `int`. This is especially important when data comes from IPC/shared memory (MTS-ESP) where the transmitter may not have initialized all values yet.

## Session 12 — M4L Architecture: Parameter Bridge + Max-Native MIDI

### Discovery: vst~ VST3 Limitations
Max's `vst~` cannot output pitch bend from VST3 plugins — it drops `kLegacyMIDICCOutEvent` events and echoes input MIDI alongside plugin output. Confirmed by:
1. Our testing: vst~ output contained Note On/Off on correct MPE channels but zero pitch bend bytes
2. ODDSound's MTS-ESP MIDI Client M4L device: uses `vst~` **only** as an MTS-ESP data bridge via parameters — ALL MIDI processing (note tracking, channel allocation, pitch bend generation) is done natively in Max

### New Architecture
Adopted ODDSound's proven approach:
1. **Receiver VST3** → pure data bridge: reads MTS-ESP tuning, exposes 128 cents-deviation parameters (`cents_0`–`cents_127`, range ±4800)
2. **Max `js` object** (`mts_midi_effect.js`) → handles all MIDI processing: note tracking, MPE channel allocation (ch 2-16 round-robin), pitch bend calculation, Mono PB mode
3. **Max patch** → `midiin` → `midiparse` → `js` → `midiout` for notes; `midiformat` for CC/PB passthrough; `vst~` + parameter polling (`uzi 128` → `get` → `unpack` → denormalize → `js`) for tuning data

### C++ Changes
- Added 128 `AudioParameterFloat` params to `ReceiverProcessor` APVTS
- Rate-limited updates: every 10 processBlock calls, only changed values (>0.01 cents threshold)
- `setValueNotifyingHost()` from audio thread — VST3 spec allows this via `IComponentHandler::performEdit()`
- Existing MIDI processing code unchanged — still works directly in Logic/Reaper

### Files Created
- `m4l/mts_midi_effect.js` — Max `js` object: MPE + Mono PB modes, 14-bit pitch bend, channel allocation
- `m4l/Arabic Maqam Tuner Receiver.maxpat` — Max patch JSON with MIDI chain, parameter polling, `live.dial` (bend range), `live.menu` (mode)
