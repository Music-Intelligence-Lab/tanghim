# 2026-02-17 — Project Inception Through First Successful Build

## The Idea

Khyam described the plugin concept: a simple maqam tuning VST for all OSs and DAWs, powered by the DiArMaqAr API. The core interface would be a tuning system selector, 12 maqam preset buttons, and 12 chromatic sliders (C through B) that snap to available pitch variations from the DiArMaqAr 12-pitch-class-set classification system.

The critical musicological point established from the start: IPN references must respect Arabic maqam theory. Microtonal modifiers indicate what a pitch is a *variant of*, not mathematical proximity to 12-EDO. So `E-b3` (segah) is a variant of **E**, not Eb. This distinction is fundamental to how the sliders work — it determines which pitch classes appear as snap positions on which slider.

## Planning Phase

### Research

Before writing any code, we researched:
- **DiArMaqAr API** — fetched the OpenAPI spec, explored endpoints for tuning systems, pitch classes, and the 12-pitch-class-sets classification
- **MTS-ESP** — studied the ODDSound master library API for shared-memory microtuning
- **JUCE 8 WebView** — Khyam specifically wanted the new JUCE 8 WebBrowserComponent for the UI, citing the blog post about WebView UIs

### Architecture Decisions

Key decisions made during planning:

1. **JUCE 8 C++ with React WebView UI** (not native JUCE components) — Khyam wanted this for easier UI development and hot-reloading during development
2. **IS_MIDI_EFFECT = FALSE** — despite being a MIDI effect conceptually, Ableton Live and FL Studio don't support MIDI effect plugins, so we set this to FALSE for DAW compatibility
3. **Three output modes:** MTS-ESP (primary, out-of-band via shared memory), MPE (per-note pitch bend across channels 2-16), and 14-bit monophonic pitch bend (legacy fallback)
4. **12-pitch-class sets as the organizing principle** — maqamat that share the same 12-note chromatic set are grouped together, making preset assignment logical
5. **Version-based update detection** — the API includes ISO 8601 timestamps on every resource; we compare these lexicographically to detect stale cached data

The full plan was written to `IMPLEMENTATION_PLAN.md` and structured into 5 milestones.

### Milestone 2: Data Model + API Layer

**Data model (`source/model/`):**
- `PitchClass.h` — the core struct, including the critical `ipnReferenceFromEnglishName()` method that strips microtonal modifiers from the API's `englishName` field (e.g. `"E-b3"` → `"E"`)
- `TuningSystem.h` — metadata about each tuning system
- `TwelvePitchClassSet.h` — a 12-note set with compatible maqamat, including `resolveSliderPositions()` for determining which variant index each slider should snap to for a given maqam
- `ActiveTuningState.h` — the live slider state with `buildFrequencyTable()` and `buildCentsDeviationTable()` generating 128-note arrays
- `MaqamPreset.h` — stored preset with 12 slider positions

**API layer (`source/api/`):**
- `DiArMaqArClient` — a `juce::Thread` subclass with a request queue; callbacks dispatched to the message thread via `MessageManager::callAsync()`
- `ApiDataCache` — in-memory + disk-backed JSON cache in the user's app data directory, keyed by `tuningSystemId:startingNote`
- `ApiResponseParser` — parses the DiArMaqAr JSON responses including the `midiNoteDeviation` string format (`"48 -5.9"`)
- `DataUpdateChecker` — compares ISO 8601 version timestamps from the API against cached versions to detect stale data

### Milestone 3: Tuning Engine

**Engine (`source/engine/`):**
- `TuningEngine` — central coordinator maintaining 128-note frequency and cents deviation tables, with a `juce::CriticalSection` guarding audio-thread reads vs message-thread writes
- `MtsEspMaster` — RAII wrapper around the MTS-ESP C API (`MTS_RegisterMaster`, `MTS_SetNoteTunings`, etc.)
- `MpePitchBendProcessor` — MPE lower zone implementation with round-robin channel allocation across channels 2-16, 48-semitone pitch bend range (covers Arabic microtonal deviations up to ~107 cents)
- `MonoPitchBendProcessor` — inserts 14-bit pitch bend before each Note On, monophonic

### Build Fixes

The first build attempt revealed several issues that needed fixing:

1. **NativeBridge API mismatch** — The code used `browser.addNativeFunction()` which doesn't exist in JUCE 8. The correct API is `Options::withNativeFunction()` registered during construction. Required restructuring `NativeBridge` to build Options rather than call methods on an existing browser, and changing construction order so `NativeBridge` exists before `WebBrowserComponent`.

2. **MTS-ESP API mismatch** — `MTS_FilterNote` takes 3 arguments `(bool doFilter, char midinote, signed char midichannel)` not 2. `MTS_ClearNoteFilter()` takes 0 arguments, not 2. And the function is called `MTS_ClearNoteFilter` not `MTS_ClearNoteFilters`.

3. **Missing juce_events header** — `DiArMaqArClient.cpp` used `juce::MessageManager::callAsync()` but only included `juce_core`. `MessageManager` lives in `juce_events`.

4. **MidiBuffer iterator** — `MidiBufferIterator` has `operator*` but no `operator->`. Test code used `it->getMessage()` which doesn't compile; fixed to `(*it).getMessage()`.

5. **Duplicate main() in tests** — Three test files each define `int main()`. Can't link them into one executable. Split into 3 separate test executables via a CMake `foreach()` loop. Also set `JUCE_STANDALONE_APPLICATION=0` to prevent JUCE from providing its own `main()`.

## Session 2: Smoke Test and API Integration Fixes

### First Launch

Started the Vite dev server (`npm run dev`) and launched the standalone plugin. **The plugin launched successfully** (JUCE v8.0.12) and the WebView established a TCP connection to the Vite dev server on port 5173 — confirming the WebView-to-React pipeline works.

### API Response Mismatch

Testing the live DiArMaqAr API revealed that the response structures were significantly different from what our parser expected. The API was reachable (35 tuning systems returned), but every response was wrapped and nested differently:

1. **Tuning systems** — Our parser expected flat `{ id, displayName, startingNotes: [{ id, displayName }] }`. Actual API returns `{ count, data: [{ tuningSystem: { idName, displayName, version, year }, startingNotes: { idNames: [...], displayNames: [...] } }] }`. The starting notes are parallel arrays, not an array of objects.

2. **Pitch classes** — Our parser looked for a `data` key. Actual API uses `pitchClasses` as the key. The MIDI deviation field is called `midiNotePlusCentsDeviation` (not `midiNoteDeviation`). Bonus: the API already provides `ipnReferenceNoteName`, so we don't always need to compute it ourselves.

3. **12-pitch-class sets** — Our parser expected `data` array. Actual API uses `sets` as the key. Source maqam is wrapped in `{ sourceMaqam: { idName, displayName } }`. Compatible maqamat have tonic info nested in `{ tonic: { ipnReferenceNoteName, noteNameIdName } }`. The pitch class array key is `pitchClassSet` (not `pitchClasses` or `slots`).

Rewrote `ApiResponseParser.cpp` to handle the actual nested structure with fallbacks for alternative key names.

### JUCE 8 JS Module API

The JavaScript bridge also needed fixing. JUCE 8 doesn't expose `window.Juce.getNativeFunction()`. Instead, it injects a proper ES module that must be imported:

```js
import { getNativeFunction } from "./juce"
```

This module is only available at runtime inside the WebBrowserComponent. In dev mode (standalone browser), it doesn't exist. Solution: dynamic `import('./juce')` with try/catch fallback in `useJuceBridge.ts`.

Event listeners also needed fixing: the callback receives data directly (already a JS object), NOT wrapped in `{ data: string }` as originally coded.

Created `ui/src/hooks/juce.d.ts` for TypeScript declarations of the runtime-injected module.

### End of Session 2 Status

- Plugin launches, WebView connects to Vite dev server
- API parsers updated to match real DiArMaqAr response structure
- JS bridge updated to use JUCE 8 module API
- All C++ builds and tests still pass
- Next: functional testing with live data flow (select tuning system → sliders populate)

## Session 3: Slider Polish, Octave Mapping, and MIDI Feedback

### Slider Layout and Visual Fixes

Multiple iterative improvements to the 12-slider interface:

1. **Even distribution** — Changed sliders and preset buttons from fixed `width: 64px` to `flex: 1; min-width: 0` so they distribute evenly across the full plugin width regardless of window size.

2. **Label alignment** — Added `margin-left: 12px` to `.ipn-label`, `.note-name`, and `.cents` to visually center them over the track (offsetting past the 8px snap-markers column + 4px gap).

3. **Removed disabled appearance** — Single-variant sliders had grey thumbs (`.thumb-locked` class) making them look inactive. Removed this class since all sliders are always "active" — having one variant is still a valid tuning choice.

4. **MIDI activity flash** — Added visual feedback when MIDI notes are received:
   - `PluginProcessor`: atomic `uint16_t midiActivityBits` set in `processBlock()` on Note On (one bit per chromatic index)
   - `PluginEditor`: 30fps Timer polls the bitmask, emits `midiActivity` event to WebView
   - React: 120ms auto-clear per bit, applies `.midi-hit` CSS class (brighter thumb + glow)

5. **Label reordering** — Moved cents deviation above the PAO note name (was below). Allowed PAO names to wrap onto two lines with `word-break: keep-all` to prevent mid-word breaks.

### The Octave Mapping Bug (Critical)

The most complex bug: PAO note names were showing the wrong octave. Sliders should display the reference octave (C3–B3: rāst, dūgāh, segāh, nawā, ḥusaynī...) but were showing sub-octave names (qarār rāst, yegāh, ʿushayrān...).

**Root cause:** The DiArMaqAr API's octave numbering is *tonic-relative*, not C-relative. For a G-based tuning system (starting note = yegāh), octave 1 spans G2–F#3. So filtering by `octave == 1` gives:
- C slot → rāst (C3) ✓ (C is above G in the octave)
- A slot → ʿushayrān (A2) ✗ (A is below G, so it's in the lower part of octave 1)

We need ḥusaynī (A3), which is in API octave 2 for this system.

**Three attempts to fix:**
1. ❌ **Filter by tonic's MIDI range** — Found tonic at octave 1, computed baseMidi. For G-based systems, tonic at octave 1 has MIDI ~43, giving baseMidi=36 (C2–B2 range). Wrong octave entirely.
2. ❌ **Filter by `octave == 1`** — Works for C-based systems where octave 1 = C3–B3. Fails for non-C-based systems where octave 1 spans a different register.
3. ✅ **Filter by MIDI note number [48–59]** — MIDI numbers are absolute (C3 = 48 regardless of tuning system). This correctly pulls from whichever API octave contains each note in the C3–B3 register.

**Key insight:** MIDI note numbers are the universal ground truth for register assignment. The API's `octave` field is tonic-relative and only useful within a single system's internal logic.

### PAO Name Preservation Across System Switches

When switching tuning systems, the plugin now matches slider positions by PAO note name (rāst, segāh, etc.) globally across all 12 slots, rather than only within the same IPN slot. This preserves musical intent when a note maps to a different IPN position in the new system.

**Algorithm:**
1. Collect all 12 previously selected PAO names into a set
2. Rebuild all slots with new system's variants (default to index 0)
3. For each slot, check if any variant's PAO name exists in the saved set — if so, select it
4. Unmatched slots keep the IPN default (first variant)

## Reflections

### On the DiArMaqAr integration
The API is well-structured for this use case. The `midiNoteDeviation` data type gives us exactly what we need: a MIDI note number and a cents deviation from 12-EDO. The `englishName` field with its microtonal modifier convention (`E-b`, `D-#`) is the key to correctly mapping pitch classes to chromatic slider positions — this is where the Arabic musicological logic lives.

### On JUCE 8 WebView
The WebView approach is powerful but requires careful attention to the bridge API. The native functions must be registered via `Options::withNativeFunction()` at construction time — there's no post-construction registration. This means the bridge object must exist before the browser, which inverts the typical ownership pattern. The payoff is hot-reloadable UI development in React while maintaining the full power of JUCE's audio/MIDI processing.

### On AI-assisted development
The initial code generation produced plausible but incorrect API calls for both JUCE 8 WebView and MTS-ESP. The JUCE WebView API is new enough that the training data likely didn't cover it well. The fix required reading the actual header files in the cloned JUCE submodule — live documentation (Context7) and source code are essential when working with newer APIs.

## Session 4: Output Mode Separation, Monophony, and Per-Note Overrides

### Separated Pitch Bend Ranges
MPE and monophonic pitch bend modes now have independent configurable range settings. Previously they shared one value, which was wrong since MPE needs a wide range (48 semitones for Arabic microtuning) while mono pitch bend typically uses 2 semitones. Each mode stores its own range, and the bridge exposes separate getters/setters.

### Monophony Enforcement
Added monophonic mode for the pitch bend output. When active, only the most recent note sounds — previous notes are killed with Note Off before the new Note On. This is essential for legato playing with 14-bit pitch bend, where polyphony would produce wrong pitches since there's only one pitch bend value per channel.

### Per-MIDI-Note Variant Selection
The most significant architectural change in this session. Previously, variant selection was per chromatic index (all C notes shared one variant, all D notes another, etc.). Now each individual MIDI note (0–127) can have its own variant override via Shift+click/drag on a slider.

**Architecture:**
- `ActiveTuningState::perNoteVariantOverrides[128]` — array of ints, -1 = no override
- `effectiveVariantIndex(midiNote)` — returns per-note override if set, otherwise falls back to the chromatic slot default
- `NativeBridge` exposes `setNoteVariant(midiNote, variantIndex)` for per-note and `setSliderVariant(chromaticIndex, variantIndex)` for chromatic-wide changes
- UI: Shift+drag applies per-note only; normal drag changes the chromatic slot default
- Visual: blue thumb glow and accent-coloured IPN label indicate per-note override

## Session 5: Resizable Slider Bank, Smooth Scrolling, and Per-Note MIDI Activity

### Smooth-Scrolling Slider Bank with Dynamic Width

**The problem:** The slider bank was fixed at 12 sliders using `flex: 1` to fill the width. The `RangeScroller` jumped in 12-note increments. Widening the window just stretched the 12 sliders.

**The solution:** A complete rework of the slider bank layout:

1. **Fixed-width sliders** — Each `NoteSlider` now has a fixed width of 68px (`constants.ts: SLIDER_WIDTH_PX`) instead of `flex: 1`. This means wider windows show more sliders rather than stretching them.

2. **ResizeObserver hook** (`useVisibleSliderCount.ts`) — Observes the slider bank container's width and computes `Math.floor(availableWidth / 68)` to determine how many sliders fit. The bank renders exactly that many sliders.

3. **Smooth scrolling** — `RangeScroller` now pans one MIDI note at a time with `max = 128 - visibleCount`. Mouse wheel on the slider bank (`onWheel` with `Math.sign(deltaY)`) also scrolls.

4. **Plugin window limits** — Increased max width from 1600 to 2400px (`PluginEditor.cpp: setResizeLimits`), allowing ~32 visible sliders at full width.

**Iterative layout tuning:** Getting the sliders to fit tightly required several rounds:
- Eliminated inter-slider gap: `NoteSliderBank.css: gap: 0`
- Removed bank horizontal padding: `padding: 8px 0`
- Removed label margin offsets: all `margin-left: 0` (the 12px offset had been needed when snap markers were in the flow)

### Centered Slider Tracks

**The problem:** Snap marker dots (8px wide) sat to the left of the slider track in the DOM flow, pushing the track right of center relative to the IPN label and PAO name text.

**The fix:** Moved snap markers inside the `.track` div and positioned them with `position: absolute; right: 100%; margin-right: 4px`. The track itself got a fixed `width: 24px` and is centered via `justify-content: center` on `.track-wrap`. Now the track bar + thumb are perfectly centered under the labels.

### Range Scroller Tick Marks

Added visual tick marks to the range slider at every C (pitch class 0), G (7), and A (9) note position. The ticks are absolutely positioned within a wrapper div, sitting behind the slider track (`z-index` layering). They help orient the user when scrolling across the MIDI range.

### Per-Note MIDI Activity (128-bit)

**The problem:** MIDI activity highlights used a 12-bit pitch-class bitmask (`uint16_t`), so playing C3 would light up ALL C sliders across every octave.

**The fix:** Changed to per-note tracking across the full pipeline:
- **C++ Processor:** `uint16_t noteOnBits` → `uint32_t noteOnBits[4]` (4 × 32 = 128 bits). Bit index = MIDI note number.
- **C++ Editor:** Timer exchanges all 4 words, iterates bits, and sends arrays of MIDI note numbers: `{ on: [60, 64, 67], off: [48] }` instead of bitmask integers.
- **JS App:** `useState(0)` (12-bit mask) → `useState<Set<number>>(new Set())`. Adds note-on numbers, deletes note-off numbers.
- **JS NoteSliderBank:** `midiActiveMask & (1 << chromaticIndex)` → `midiActiveNotes.has(midi)`.

Now only the exact MIDI note being played highlights gold — octave duplicates stay dark.

### Visual: Gold MIDI Highlight

Changed the MIDI hit thumb colour from pink (`#ff6b8a`) to gold (`#ffc947`) for better visual distinction from the default slider thumb colour.

## Session 6: Maqam Selector and Preset Assignment System

### The Problem

The `TwelvePitchClassSet` infrastructure (model, parser, API client) existed in C++ but was **never wired up** — `PluginProcessor::currentSets` was declared but always empty. The existing `MaqamPickerDialog` (right-click on preset) was non-functional because of this gap.

### UX Decisions

After discussion with Khyam:
- **Maqam selection:** Two dropdown selectors in a new row below the tuning system selector — first for base maqam, second for variants/transpositions
- **Preset saving:** Click any empty preset slot to save the current maqam selection there
- **Preset clearing:** Small × button appears on hover over assigned presets
- **Active indicator:** Applied preset gets highlighted border/background

### C++ Backend Changes

**Wiring up the data pipeline:**
1. `PluginProcessor::fetchSetsIfNeeded()` — new method called at the end of `loadTuningSystem()`. Checks cache first, falls back to `apiClient.fetchTwelvePitchClassSets()`.
2. `PluginProcessor::applyMaqamFromSet(int setIndex)` — resolves slider positions in batch using `resolveSliderPositions()`, clears per-note overrides, applies all 12 positions with a single `tuningEngine.updateTuning()` call.
3. `ApiDataCache::updateSets()` — stores sets in cache entry for disk persistence.
4. `ApiDataCache` serialization — full JSON serialization/deserialization of `twelvePitchClassSets` (source maqam, slots, compatible maqamat).
5. `NativeBridge` — new `applyMaqamFromSet` bridge function, updated `assignPreset` to accept full maqam metadata (9 args: baseMaqamId, isTransposed, tonicNote, tonicIpn, setIndex).
6. `PluginEditor` — wired `onMaqamSetsLoaded` callback to push `maqamSetsLoaded` event to WebView.

### React UI Changes

**New components:**
- `MaqamSelector` — two `CustomSelect` dropdowns (base maqam + variant/transposition). Flattens all sets → groups by `baseMaqamId`. Base maqam dropdown is searchable. Auto-selects first non-transposed variant when base changes.
- `CustomSelect` enhanced with `searchable` and `placeholder` props — search input at top of dropdown, filters options case-insensitively.

**Reworked components:**
