# 2026-02-27 — Session 45: Maqam List Loading Performance + Preset Compatibility + Cache Status Indicators

## Problem: Slow Maqam List Loading on DAW Session Start

On fresh plugin load into a DAW session, the default tuning system (al-Fārābī 950g) was taking too long to show its maqamat and validate presets. Presets would flash as "not available" before the maqam list arrived.

### Root Cause: Event Ordering in `doLoad()`

In `PluginProcessor.cpp`, `loadTuningSystem()`'s `doLoad()` lambda had this order:

```
1. notifyTuningChanged()       ← emits tuningStateChanged to JS (presets rendered)
2. onComplete()                ← session recall also calls notifyTuningChanged()
3. saveSettingsToDisk()
4. fetchMaqamListIfNeeded()    ← emits maqamListLoaded to JS (AFTER presets)
```

The UI received `tuningStateChanged` with preset data BEFORE `maqamListLoaded`. In `MaqamPresetBar.tsx`, `isPresetCompatible()` checks `maqamList.find(m => m.maqamId === preset.maqamId)` — but `maqamList` was still empty, so all assigned presets showed as "not available" until the maqam list event arrived.

The maqam list IS in the cache file (confirmed: `alfarabi_950g_ushayran.json` has 54 maqam entries, 303KB total). The data wasn't slow to read — it was just delivered to the UI in the wrong order.

### Fix 1: Reorder `doLoad()` — maqam list before tuning state notification

Moved `fetchMaqamListIfNeeded()` before `notifyTuningChanged()` so the maqam list is populated and the `maqamListLoaded` event reaches JS first:

```cpp
// Before:
notifyTuningChanged();
if (onComplete) onComplete();
saveSettingsToDisk();
fetchMaqamListIfNeeded();  // too late

// After:
fetchMaqamListIfNeeded();  // populate maqam list first
notifyTuningChanged();
if (onComplete) onComplete();
saveSettingsToDisk();
```

### Fix 2: Disable presets when maqam list is empty

In `MaqamPresetBar.tsx`, `isPresetCompatible()` now returns `false` when `maqamList.length === 0` — assigned presets are disabled until the list confirms compatibility. This prevents users from clicking an invalid preset during system/starting note switches.

```tsx
if (maqamList.length === 0) return false  // not yet loaded — disable until confirmed
```

### Fix 3: Deactivate incompatible active preset after system switch

Added a `useEffect` in `App.tsx` that checks the active preset's compatibility when a new maqam list arrives. If the active preset's maqam isn't in the new list, `activePresetIndex` is reset to `-1`, removing the active styling.

```tsx
useEffect(() => {
  if (activePresetIndex < 0 || maqamList.length === 0) return
  const preset = tuningState.presets[activePresetIndex]
  if (!preset?.isAssigned) return
  const entry = maqamList.find(m => m.maqamId === preset.maqamId)
  if (!entry || (preset.isTransposed && ...)) setActivePresetIndex(-1)
}, [maqamList, activePresetIndex, tuningState.presets])
```

## Feature: Cache Status Indicators in Tuning System Selectors

Added per-item indicators in both the tuning system and starting note dropdown lists showing whether data is cached locally (`✓` green) or needs downloading (`↓` grey).

### C++ Changes

- **`PluginProcessor.h/cpp`**: Added `hasCachedTuningData(systemId, startingNote)` public method that delegates to `dataCache.hasData()`.
- **`NativeBridge.cpp`**: `buildTuningSystemsJson()` now includes `isCached` boolean per starting note.

### UI Changes

- **`types/index.ts`**: Added `isCached?: boolean` to `StartingNote` interface.
- **`CustomSelect.tsx`**: Extended `Option` interface with optional `suffix` and `suffixClass` fields. Suffix renders right-aligned in the dropdown. Changed `.cs-option` from `display: block` to `display: flex` with label and suffix spans.
- **`CustomSelect.css`**: Added `.cs-option-suffix` base style, `.cached` (green `#66bb6a`, 0.8 opacity), `.uncached` (grey `#888`, 0.4 opacity).
- **`TuningSystemSelector.tsx`**: System options show `✓`/`↓` based on first starting note's cache status. Starting note options show per-note status.
- **`App.tsx`**: `onTuningStateChanged` marks the loaded system+note as `isCached: true` in React state so indicators update live after loading a system.

### Bug Fix: `loadFromDisk()` Key Reconstruction

The cache status indicators revealed a pre-existing bug in `ApiDataCache::loadFromDisk()`. The filename→key conversion used `replaceCharacter('_', ':')` which turned ALL underscores into colons:

```
Filename: alfarabi_950g_ushayran.json
Wrong key: alfarabi:950g:ushayran
Correct key: alfarabi_950g:ushayran
```

Only the separator between system ID and starting note should be a colon. Since starting note names never contain underscores, the fix replaces only the **last** underscore:

```cpp
// Before:
const juce::String key = f.getFileNameWithoutExtension().replaceCharacter ('_', ':');

// After:
const auto name = f.getFileNameWithoutExtension();
const auto lastUnderscore = name.lastIndexOfChar ('_');
if (lastUnderscore <= 0) continue;
const auto key = name.substring (0, lastUnderscore) + ":" + name.substring (lastUnderscore + 1);
```

This bug meant `hasData()` returned `false` for all cached entries on startup (since the reconstructed key didn't match). It only "worked" because entries were re-cached into the correct in-memory key format when actually loaded via `storeData()`. The bug was hidden because `loadTuningSystem()` always went through the full preload→doLoad path rather than short-circuiting on cache hits.
