## Session 39: MIDI Preset Device Selector Fix

### Problem

The MIDI device selector in the status bar (used for preset MIDI map triggering) was not working properly — selecting a device wouldn't register it, or the device would stop working after disconnect/reconnect cycles.

### Root Cause Analysis

Three interacting bugs in the MIDI device lifecycle:

**1. Stale `midiPresetInput` pointer after device disconnect**

When a MIDI device is unplugged, JUCE doesn't automatically invalidate the `MidiInput` unique_ptr — it stays non-null even though the underlying CoreMIDI connection is dead. This caused:
- `isMidiPresetDeviceOpen()` returning `true` for a dead connection
- The editor timer's reconnection check (`!processor.isMidiPresetDeviceOpen()`) being skipped
- No automatic reconnection when the device was plugged back in

**2. Idempotency check blocked same-device reconnection**

```cpp
// OLD — problematic
if (deviceName == midiPresetDeviceName && midiPresetInput != nullptr)
    return;
```

Even if reconnection was somehow triggered, this early return prevented reopening: the name matched and the (stale) pointer was non-null. The fix was to remove this check entirely and always close+reopen — the method now unconditionally stops and resets any existing input before opening the new device.

**3. Name-only persistence (no device identifier)**

JUCE `MidiDeviceInfo` has both `name` (human-readable, NOT unique) and `identifier` (OS-unique string). Only the name was persisted, so if two devices shared a name, or if the identifier changed across reconnections, matching could fail.

### Fix Details

**`recheckMidiPresetDevice()` — new method** (`PluginProcessor.h/.cpp`)
- Called from the editor timer when `midiDevicesChanged` fires (CoreMIDI notification)
- Checks if the currently open device's identifier or name still appears in `MidiInput::getAvailableDevices()`
- If the device disappeared, closes the stale connection (`stop()` + `reset()`) while preserving `midiPresetDeviceName` so the timer's existing reconnection logic can attempt reopening

**`setMidiPresetDevice()` — rewritten** (`PluginProcessor.cpp`)
- Removed the faulty idempotency check — now always closes existing input before opening
- Two-phase device matching: tries saved identifier first (fast, reliable), falls back to name match
- Stores `midiPresetDeviceId` on successful open for future matching
- Comprehensive DBG logging at each step: requested device, current state, match method, success/failure with identifier

**Identifier persistence** (`PluginProcessor.h/.cpp`)
- New `midiPresetDeviceId` member alongside `midiPresetDeviceName`
- Saved to `~/Library/Tanghim/settings.json` as `"midiPresetDeviceId"`
- Loaded before `setMidiPresetDevice()` so identifier match can be tried first on startup

**Editor timer update** (`PluginEditor.cpp`)
- `recheckMidiPresetDevice()` called **before** `populateMidiDeviceList()` on device list change
- This ensures stale connections are cleaned up before the reconnection attempt runs

**Explicit `juce_audio_devices` CMake link** (`CMakeLists.txt`)
- Was previously only linked transitively through `juce_audio_utils`
- Now explicit in `target_link_libraries` for clarity and safety

**Diagnostic logging** added to:
- `setMidiPresetDevice()`: logs requested device, current state, match method, identifier, success/failure
- `handleIncomingMidiMessage()`: logs received note number, channel, filter state, learn target
- `recheckMidiPresetDevice()`: logs when stale connection detected and closed

### JUCE 8 MidiInput Architecture Notes

Investigated the JUCE 8 `MidiInput::openDevice` implementation during debugging:
- Uses UMP (Universal MIDI Packet) session model internally: `getLegacySession()` → `session->connectInput()`
- Session is a shared_ptr held by `MidiInput::Impl` — stays alive as long as any `MidiInput` exists
- `MidiDeviceListConnectionBroadcaster` maintains the device registry — `getEndpointGroupForId()` / `getInfoForId()` for lookups
- Device identifiers are OS-specific (numeric strings on macOS via CoreMIDI)
- `MidiDeviceListConnection::make()` fires callback on CoreMIDI notification thread — must use atomic flag + message thread handoff (which we already do)

### Data Flow (After Fix)

```
Device plugged in/out
    ↓
CoreMIDI notification → MidiDeviceListConnection callback
    ↓
midiDevicesChanged.store(true) [atomic]
    ↓
Editor timer (2Hz mtsStatus branch)
    ├─ recheckMidiPresetDevice()     ← NEW: detect stale, close dead connection
    ├─ populateMidiDeviceList()      ← rebuild ComboBox
    └─ if (name.isNotEmpty() && !isOpen())
           setMidiPresetDevice(name) ← try identifier first, then name match
```
